## Open Questions

### Runtime & Isolation

**Q1. Kata Containers vs. Firecracker — which runtime?**  
Kata is more mature with broader tooling support. Firecracker (used by AWS Lambda) is leaner and purpose-built for short-lived workloads but requires more integration work. Which fits the operational model here?

**Q2. What kernel version / image is used inside the microVM?**  
The microVM kernel is a real attack surface. Who manages updates? Is this a shared base image per project stack or per invocation?

**Q3. Is gVisor a viable middle ground?**  
gVisor intercepts syscalls without a full VM, lighter weight than Kata/Firecracker but weaker isolation. Is it sufficient if we accept that kernel exploits are out-of-scope?

---

### Network

**Q4. How do we handle DNS-over-HTTPS exfiltration?**  
An adversarial agent could bypass the controlled DNS resolver by making DoH requests to a public resolver (e.g., `1.1.1.1` on port 443, which is also HTTPS). Blocking by IP would require maintaining a blocklist of known DoH providers. Is this worth addressing, or accepted risk?

**Q5. What is the right granularity for the network allowlist?**  
Hostname/SNI-level enforcement is achievable without TLS inspection. Path-level enforcement requires a MITM proxy with an injected CA cert. Is path-level control required, or is hostname sufficient for the threat model?

**Q6. How are CDN-hosted resources handled?**  
Many documentation and package registry resources share CDN infrastructure (e.g., `fastly.net`, `cloudfront.net`). Allowlisting at the CDN domain defeats the purpose; allowlisting by resolved IP is brittle. Is there a workable approach, or is this an accepted gap?

**Q7. How is the research role's web search access scoped?**  
The research phase needs broad web access for documentation and references. Pre-enumerating all allowed domains isn't feasible. Options: (a) allow all HTTPS outbound for research role with full audit logging, (b) proxy through a search API that itself enforces scope, (c) accept broad access for read-only phases only. Which?

### Git & Credentials

**Q8. How are GitHub App installation tokens generated and injected?**  
This requires a GitHub App installed on the repo, a secret key managed outside the container, and a token generation step at invocation time. What is the infrastructure for this? Is a GitHub App per organization, or per repo?

**Q9. What prevents a credential injected as an environment variable from being exfiltrated?**  
Environment variables are readable by any process in the container. The agent has shell access. The token will be visible. The mitigation is that the token expires and is minimally scoped — but is there a better injection mechanism (e.g., a git credential helper that doesn't expose the raw token)?

**Q10. How is branch naming managed to prevent collisions?**  
Multiple concurrent agent invocations on the same repo need distinct branch names. Is this generated by the container orchestrator, derived from the ticket ID, or left to the agent?

**Q11. Should the agent be able to read git history of the cloned repo?**  
A shallow clone limits history. But git history may contain sensitive data from past commits (removed secrets, etc.). Should history depth be zero (just working tree) or some minimum for context?

---

### Filesystem & Secrets

**Q12. How are project secrets (`.env`, credentials) handled in the clone?**  
The agent clones the repo. If `.env` or secret files are gitignored they won't appear. But if they were ever accidentally committed and are in history, a shallow clone still has them. Should the clone be post-processed to scrub sensitive paths?

**Q13. Should sensitive files be explicitly bind-blocked even if present in the clone?**  
An AppArmor/SELinux rule could deny reads on specific paths (e.g., `*.env`, `*credentials*`) even within the working directory the agent owns. Is this worth the complexity?

---

### Dependency & Test Execution

**Q14. Should the implement role be allowed to install new packages?**  
If `npm install` or `pip install` is allowed, the agent can pull arbitrary code into the execution environment. Options: (a) pre-populate a vendor directory / lockfile before the agent starts, (b) allow package installation but restrict to an approved registry, (c) allow unrestricted package installation and accept the risk. Decision has significant security implications.

**Q15. How is the test runner sandboxed?**  
The agent writes tests and runs them. Test code executes with full container permissions. An adversarial agent could write a test that makes outbound connections, reads environment variables, or exfiltrates data through the allowed git/network channels. Options: (a) accept this as within the container boundary, (b) run the test runner in a nested sandbox with tighter constraints, (c) disallow test execution entirely (agent ships code, human runs tests).

---

### Policy & Catalog

**Q16. Where does the policy catalog live and who can modify it?**  
The policy files must be outside the repo (separate trust domain from the agent). Where are they stored? How are changes to them reviewed and deployed? Who has write access?

**Q17. How is per-invocation narrowing expressed?**  
The role sets a base policy. The QRSPI plan knows the slice scope (e.g., "only touches `src/api/`"). Can the container orchestrator apply additional constraints on top of the role policy per invocation, without modifying the base role policy?

**Q18. Should the agent know its own constraints?**  
If the policy catalog is outside the repo, the agent cannot read it directly. But it can probe its environment (try a network connection, observe a denial). Should the constraint policy be actively hidden, or is it acceptable for the agent to discover its own limits through probing?

---

### Audit & Observability

**Q19. What is the audit log retention and access policy?**  
Who can read audit logs? How long are they retained? Are they associated with the PR they produced? This matters for incident response and for training signal if logs are used to improve policies.

**Q20. What constitutes an alertable event vs. expected behavior?**  
A research agent making many outbound DNS queries is expected. The same pattern from an implement agent may indicate DNS exfiltration. How are alert thresholds set, and who is notified?

**Q21. Is real-time alerting required, or is post-hoc analysis sufficient?**  
Falco supports real-time rule-based alerting. auditd is primarily for post-hoc review. Does the system need to stop or kill a container mid-run if a violation is detected, or is it sufficient to flag it after the fact?

## Research Topics

### Container Runtime
- Firecracker jailer component — designed specifically for adversarial workload isolation
- Kata Containers vs. Firecracker: operational tradeoffs for short-lived agentic workloads
- gVisor syscall compatibility surface and known bypass techniques
- microVM image management: shared base images vs. per-invocation builds

### Network Enforcement
- DNS exfiltration techniques and mitigations (rate limiting, entropy analysis, resolver interception)
- Forward proxy options for HTTPS inspection: Squid, mitmproxy, Envoy — operational complexity vs. control
- iptables vs. nftables for dynamic per-container rule management
- Network policies in Kubernetes (if orchestration moves that direction): Calico, Cilium eBPF-based enforcement

### Audit & eBPF
- Falco vs. Tetragon: rule expressiveness, performance overhead, Kubernetes integration
- auditd limitations at scale: log volume, performance impact on container workloads
- eBPF-based network flow logging: what visibility is available without TLS inspection
- Immutable log sinks: append-only S3, write-once storage options

### Git & Credentials
- GitHub App installation token generation: scoping, expiry, rotation
- git credential helper design: injecting tokens without exposing them in env or process list
- Shallow clone security properties: what history is included at `--depth=1`

### Dependency Safety
- Dependency lockfile strategies for offline/pre-populated installs (npm, pip, go modules)
- Private package registry proxies: Artifactory, Verdaccio — routing agent installs through controlled mirror
- Package integrity verification: hash pinning, sigstore/cosign for supply chain assurance

### Comparable Systems
- Dagger: per-pipeline network isolation and caching model
- GitHub Actions: runner isolation model, network egress controls
- Seatbelt (macOS) and nsjail (Linux): fine-grained process sandboxing for comparison
- AWS Lambda + Firecracker: how Amazon manages per-function isolation at scale
