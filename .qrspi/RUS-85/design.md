# Design — Structured phase-gate event log (systematic logging)

**Ticket:** RUS-85
**Research basis:** research.md @ 2026-06-18T00:00:00Z
**Generated:** 2026-06-18T00:00:00Z
**Status:** draft

## Current State

The qrspi pipeline has **no event-emission layer**: phase boundaries are marked only by two runner-injected, fire-and-forget console functions, `phase(<name>)` and `log(<string>)`, neither of which is defined in the codebase or produces structured output (ref: Q1). All phase orchestration lives in `.claude/workflows/qrspi-batch.js`, where the single chokepoint `runPhase(...)` already forks cleanly into reuse / producer-success / persist-gate / failure branches, and the per-ticket dispatch `switch (a)` (with its surrounding `try/catch`) is where ticket-level success and `action: 'errored'` failure are recorded (ref: Q1). Per-phase outcome is propagated three ways that already converge on the orchestrator: every `scripts/qrspi_*.py` prints one JSON envelope to stdout carrying `ok` (mirrored in its exit code), workers re-parse results through `parse*Envelope` validators that degrade a null/garbled result to `{ok:false}` rather than throwing, and `runPhase` returns an authoritative boolean driven by the persist gate (ref: Q2).

At every transition the **ticket ID** (`t.id`, shape `RUS-\d+`), a **phase** string (`Design | Plan | Implementation | Finalize | ...`), and an **actor/label** (`revise:RUS-8`, `persist:RUS-8:design`) are already present on each `agent()` spawn; `runId` is computed once per invocation and already stamped on every metrics ledger line (ref: Q3). The schema fields `trace_id`, `span_id`, and `parent_span_id` have **no existing source** and must be generated (ref: Q3). Any generated id must avoid `Date.now()`/`Math.random()` for resume-safety and use `crypto.randomUUID`/`getRandomValues` or an injected value (ref: Q1, Q3).

For disk writes, a strong uniform convention exists: all paths resolve the **main checkout root** via `qrspi_paths.resolve_repo_root(...)` (never a worktree), and an **append-only JSONL writer already exists** as a near-exact template in `qrspi_metrics_append.py` (`open(path,"a")`, `json.dumps(line)+"\n"`, verify-non-empty, fail closed) (ref: Q4). However, every existing `.qrspi/` path is **per-ticket and inside the worktree** (`.worktrees/<id>/.qrspi/<id>/...`); the proposed repo-level `.qrspi/observability/events.jsonl` (no `<id>` segment) would be the first cross-ticket shared write target (ref: Q4, Q9). Config is read either flat-single-key-string-only via `qrspi_config.py` (which rejects non-string and nested values) or via a dedicated typed resolver like `qrspi_critics_config.py` for structured multi-value blocks (ref: Q5). There is **no shared CLI wrapper**: each script is standalone, no script uses Python `logging` or a `--log-level` flag, and stdout is reserved for the single machine-parsed JSON envelope — so any human/structured log must go to **stderr** (ref: Q6, Q13). This is load-bearing for the ticket's *Structured logging in the CLI* scope item: because there is no wrapper, satisfying "all commands emit" forces a **per-command** install of the logger (resolved in Decision 8 / the per-command Delta retrofit), not a single centralized hook (ref: Q6). The existing crash-safe idiom is staging-then-`shutil.move` for whole-file artifacts; the append path only verifies non-empty and has **no torn-line/fsync protection** (ref: Q10). Unit tests are stdlib-only `scripts/*_test.py` siblings run via `run_tests.py`, exercising pure helpers against `tempfile` roots so the real `.qrspi/` tree is never touched (ref: Q12).

**Three ticket premises do not hold against the code** (ref: Q7, Q11, Q9): no exponential-backoff retry policy exists anywhere (only the `ciReviseCap` consecutive-red *count* cap and fixed "retry once" prose — ref: Q7); no log rotation, size-threshold, or current-file selection exists (ref: Q11); and the per-ticket isolation that is the *only* current concurrency guarantee would be broken by a single shared file with no lock/fsync/`O_APPEND` guard (ref: Q9).

## Desired End State

Mapping each ticket acceptance criterion to concrete behavior:

- **Every phase transition produces a structured event (start, end, success, failure, retry).** A new event-emitter is invoked at the existing transition forks in `runPhase` (reuse/start, success, failure) and at the per-ticket dispatch outcome (success push / `errored`), plus the CI-revise increment point for retry events (ref: Q1, Q8). No new transition points are invented — emission piggybacks on already-clean forks.
- **Events appended to a single JSONL file at `.qrspi/observability/events.jsonl`.** A new self-locating writer script computes this repo-root path (never typed by a worker) and appends one JSON line per event, following the `qrspi_metrics_append.py` template (ref: Q4). See Decision 1 for the path-shape trade-off the ticket's literal path forces.
- **Append-only, append-aligned, never rewritten (crash-safe).** Each event is one self-contained line written in a single `os.write` of an assembled bytes blob terminated by `\n`, so a crash leaves at most a torn final line that JSONL readers drop — the writer adds the torn-line tolerance the codebase currently lacks (ref: Q10).
- **Standard event schema** (`event_id`, `trace_id`, `span_id`, `parent_span_id`, `timestamp`, `event_type`, `ticket_id`, `phase`, `actor`, `status`, `message`, `context`). `ticket_id`, `phase`, `actor`, `event_type`, `status`, `message` source from existing transition data; `trace_id` is `${runId}:${t.id}` (per-ticket, correlatable with the metrics ledger); `event_id` and `span_id` are generated per event via `crypto.randomUUID`; `parent_span_id` is set to the per-ticket `trace_id` (the ticket-run span every transition hangs off) or `null` where no parent is materialized — **no `parentSpanId` is threaded through the JS call chain** (see Decision 5); `timestamp` is injected by the JS emitter as an explicit argument and stamped by the writer's pure assembler from that argument (the writer's I/O layer supplies a Python-`time` wall-clock default only when no timestamp is passed), keeping the assembler pure (see Decision 6) (ref: Q3, Q1).
- **Error and retry tracking with failure message, error code, backoff duration.** Error and retry-attempt events carry, in the schema's `context` map: the **failure message** (`message` field), the **error code** (`context.error_code`, sourced from the failing `qrspi_*.py` envelope's `error` string / the JS-level `errored` marker — every script mirrors `ok` in its exit code and carries an `error` string on failure, ref: Q2), and the `CI-Revise-Attempt` counter + `ciReviseCap` (read, never mirrored, from the gather's red-gated `ciReviseAttempt` / the bump worker's `{prior,new}`, ref: Q8). The `error_code` requirement is satisfied by mapping it into the optional `context` map rather than adding a 13th top-level field — see Decision 7. **There is no backoff duration to record** (no backoff policy exists, ref: Q7) — this single ticket-named attribute is explicitly deferred, see Open Questions OQ1.
- **Log rotation (default 10 MB) and retention (default 30 days), compress + archive old files.** Greenfield: the writer checks file size before each append and, on threshold, renames the current file to a timestamped archive and gzips it; a retention sweep prunes archives older than the configured age (ref: Q11). See Decision 3 and OQ2.
- **Structured JSON logs from the CLI commands to file and optionally stderr; configurable log level; context always carries ticket ID, phase, trace ID.** This is a **distinct ticket requirement from the phase-gate event log above** — it covers the per-command logs the standalone `scripts/qrspi_*.py` commands emit, not the orchestrator's phase-transition events. The shared `qrspi_obs.py` module exposes a per-command structured logger (`get_logger(*, ticket_id, phase, trace_id, level, stream=sys.stderr)`) imported the same way `qrspi_paths` is. Because research Q6 establishes there is **no shared CLI wrapper** ("would have to be installed per-command"), each `scripts/qrspi_*.py` command **is retrofitted to construct this logger in its `main()` and emit its own start/outcome JSON log lines** carrying the mandatory `ticket_id`, `phase`, and `trace_id` context on **every** record (Decision 8 / Delta). **Destination (`to a file`):** these general CLI logs append to the **same** `.qrspi/observability/events.jsonl` sink as the phase-gate events (one queryable trace, not a second file) — the per-command logger writes through `qrspi_obs.append_event` with an `actor` of the command name and an `event_type` of `cli_log`, so the file destination is the shared events log and the rotation/retention rules apply uniformly. The **optional stderr channel** is the human-interactive mirror (never stdout — stdout is the reserved JSON envelope, ref: Q6, Q13), gated on `--log-level`. Level + rotation-size + retention read through the dedicated typed `observability` config resolver (ref: Q5). The `trace_id` available to a Python command is sourced from `QRSPI_RUN_ID` + the command's ticket argument (`${QRSPI_RUN_ID}:${ticket}`, the same shape the JS emitter uses), so the CLI log lines and the orchestrator events share one correlatable trace id (ref: Q3).

## Delta

- **New file `scripts/qrspi_obs.py`** — the shared observability module: pure `event_path(repo_root)` (→ repo-root `.qrspi/observability/events.jsonl`), pure `build_event(*, timestamp, ...)` (schema assembly only — takes the `timestamp` as a required argument and reads NO clock, so it is deterministic and unit-testable), pure `should_rotate(size, max_bytes)` and `archive_name(...)`, and an I/O `append_event` (single-`os.write` line under a file lock — and the layer that supplies a `time.time()` wall-clock default when the caller passed no timestamp, then calls the pure `build_event`) + `rotate`/`retention_sweep` + a thin `main()` emitting the standard `{ok, ...}` envelope. **It also exposes the per-command CLI logger** the Python commands install per Q6: a pure `cli_log_record(*, ticket_id, phase, trace_id, level, message, context, timestamp)` builder (schema-shaped like `build_event`, `event_type="cli_log"`, `actor=<command name>`, so it is unit-testable with an injected timestamp) and a thin `get_logger(*, ticket_id, phase, trace_id, level, stream=sys.stderr)` factory whose `.debug/.info/.warn/.error` methods (a) append a `cli_log` record to the shared `events.jsonl` via `append_event` (the `to a file` destination) and (b) when the level threshold is met, mirror a one-line JSON record to `stream` (stderr by default — never stdout). Imported via `sys.path.insert(0, ENGINE_ROOT); import qrspi_obs` like every sibling. The clock lives in the I/O layer; `build_event`/`cli_log_record` stay pure (see Decision 6).
- **Modified `scripts/qrspi_*.py` command scripts (the per-command retrofit Q6 requires)** — each existing standalone command (`qrspi_persist.py`, `qrspi_resolve.py`, `qrspi_config.py`, `qrspi_pr_state.py`, `qrspi_ci_revise_bump.py`, `qrspi_metrics_append.py`, `qrspi_persist`, `qrspi_comment_reply.py`, `qrspi_pr_body.py`, `qrspi_provision.py`, …) gains a single shared snippet in its `main()`: read `--log-level` (default `info`, also honoring the `observability` config level) and the ticket arg, construct `logger = qrspi_obs.get_logger(ticket_id=<ticket>, phase=<command's phase or "cli">, trace_id=f"{os.environ.get('QRSPI_RUN_ID','')}:{<ticket>}", level=<level>)`, and emit `logger.info("start", ...)` and a terminal `logger.info/error(...)` carrying the command's `ok`/`error`. This is the "installed per-command" half of Q6's resolution — there is no shared wrapper to hang it on, so the logger is constructed in each `main()` (one import + ~3 lines), keeping stdout reserved for the single JSON envelope and routing all log output to the `events.jsonl` file + optional stderr. Commands with no ticket argument (e.g. a bare `qrspi_config.py --key`) log with `ticket_id=null`; the mandatory context is "ticket/phase/trace whenever available," and the trace id still anchors on `QRSPI_RUN_ID`. See Decision 8.
- **New file `scripts/qrspi_obs_test.py`** — stdlib-only sibling exercising the pure helpers (`event_path`, `build_event` with an injected fixed `timestamp`, `cli_log_record` asserting the mandatory `ticket_id`/`phase`/`trace_id` context is present on every record and `event_type=="cli_log"`, `should_rotate`, `archive_name`) and the append/rotate/sweep + `get_logger`-writes-to-tempfile I/O against `tempfile` roots (ref: Q12). The per-command retrofit's pure record-builder is covered here; the ~3-line `main()` wiring in each command is left to manual e2e like every other subprocess/IO `main` (ref: Q12).
- **Modified `.claude/workflows/qrspi-batch.js`** — add an `emitEvent(...)` helper that spawns one verbatim-command worker per event (the delegate-to-worker pattern, like `persistArtifact`), passing `traceId` (`${runId}:${t.id}`), a freshly-generated per-event `span_id`, and `parent_span_id = traceId` (NO `parentSpanId` argument is threaded through `doDesign/doPlan → runPhase`; the parent is the flat per-ticket trace id, see Decision 5), an explicit injected `timestamp`, and (for error/retry events) an `error_code` into `context`. Call `emitEvent` at the existing forks in `runPhase`, the dispatch `switch`/`try-catch`, and `bumpCiReviseTrailers`. Add `parseObsEnvelope` (degrade null/garbled to `{ok:false}`).
- **New config resolver `scripts/qrspi_obs_config.py` (+ test)** — reads the `observability` block from `.qrspi/config.json` once, coerces/defaults `logLevel`/`rotationBytes`/`retentionDays`, emits a typed `{ok, level, rotationBytes, retentionDays, warnings}` envelope (the `qrspi_critics_config.py` pattern); `parseObsConfigEnvelope` on the JS side (ref: Q5).

## Pattern Decisions

### Decision 1: Shared event-log path shape

| Option | Approach | Pros | Cons |
|--------|----------|------|------|
| A | Repo-root shared `.qrspi/observability/events.jsonl` (the ticket's literal path) | Single queryable log; matches ticket text exactly | First cross-ticket shared write target; needs a NEW lock/atomicity guarantee the codebase lacks (ref: Q9); breaks per-ticket isolation |
| B | Per-ticket `.worktrees/<id>/.qrspi/<id>/events.jsonl`, merged on query | Reuses existing isolation; zero new concurrency machinery; mirrors metrics ledger exactly (ref: Q4, Q9) | Diverges from the ticket's literal path; querying needs a merge step |

**Recommendation:** Option A, with an explicit OS file lock (`fcntl.flock`) + single-`os.write` line under PIPE_BUF guarding each append.
**Rationale:** The ticket names a *single* JSONL file as a hard requirement and the value (a queryable cross-pipeline trace) depends on one sink. The codebase has no shared-file precedent (ref: Q9), so the atomicity guarantee is genuinely new regardless; Option A confines that novelty to one well-tested writer rather than spreading a merge step across every query consumer (RUS-86).
**NEW PATTERN?** Yes — first repo-level shared `.qrspi/` write target and first file-locked append; justified because per-ticket isolation (ref: Q4, Q9) cannot satisfy a single-file requirement, and `flock` is the minimal addition that makes a shared append safe.

### Decision 2: Where event emission attaches

| Option | Approach | Pros | Cons |
|--------|----------|------|------|
| A | Emit at existing `runPhase`/dispatch/bump forks via a JS `emitEvent` helper delegating to a worker | Reuses the clean start/success/failure forks already present (ref: Q1); honors the JS-delegates-to-worker rule (ref: Q1) | One extra worker spawn per transition |
| B | Emit inside each Python script's `main()` | Closer to authoritative `ok`; no JS change | Scattered across many standalone scripts (no shared wrapper, ref: Q6); misses JS-only transitions (dispatch `errored`, reuse) |

**Recommendation:** Option A.
**Rationale:** `runPhase` and the dispatch `try/catch` are the only points that see *every* transition including JS-level `errored` and reuse (ref: Q1, Q2); Python scripts see only their own slice. The delegate-to-worker emit matches how `persistArtifact`/`recordCriticMetrics` already work (ref: Q1).
**NEW PATTERN?** No — reuses the established delegate-to-worker + `parse*Envelope` pattern.

### Decision 3: Rotation / retention ownership

| Option | Approach | Pros | Cons |
|--------|----------|------|------|
| A | Inline in the same `append_event` call (check size, rotate, gzip, sweep before/after each append) | Atomic with the write under the same lock; no scheduler | Adds latency to some appends; sweep on every call is wasteful |
| B | Separate `qrspi_obs --rotate` invocation called once per batch run | Keeps append fast; sweep amortized | Rotation lag can overshoot the size cap; second invocation point |

**Recommendation:** Option A for rotation (size-triggered, under the lock), Option B's amortization for retention (sweep once per run, not per append).
**Rationale:** Rotation must be transactional with the write to avoid a torn record at the boundary (ref: Q10, Q11) — only holding the append lock guarantees the current-file pointer is consistent. Retention is time-based and tolerates lag, so a once-per-run sweep avoids per-append cost. No precedent exists for either (ref: Q11), so both are designed from scratch.
**NEW PATTERN?** Yes — no rotation/retention anywhere today (ref: Q11); justified because the ticket requires size rotation + dated retention and there is nothing to reuse.

### Decision 4: Observability config reader

| Option | Approach | Pros | Cons |
|--------|----------|------|------|
| A | Flat string keys via `qrspi_config.py` (`"logLevel":"info"`, `"rotationBytes":"10485760"`) | Reuses existing reader | Reader is string-single-key only and rejects ints/nested (ref: Q5); forces stringly-typed numbers |
| B | Dedicated typed resolver `qrspi_obs_config.py` emitting `{ok, level, rotationBytes, retentionDays, warnings}` | Type coercion + defaults + warnings in one place; mirrors `qrspi_critics_config.py` (ref: Q5) | One new script + test |

**Recommendation:** Option B.
**Rationale:** Three typed values (string level, two ints) with defaults is exactly the structured-config case the critics resolver already solves; `qrspi_config.py` cannot return ints or a nested block (ref: Q5), and `ciReviseCap` already proves a flat int is read *outside* that path (ref: Q5, Q7).
**NEW PATTERN?** No — reuses the `qrspi_critics_config.py` typed-resolver pattern.

### Decision 5: `parent_span_id` — flat default vs. materialized span threading

| Option | Approach | Pros | Cons |
|--------|----------|------|------|
| A | Generate a `span_id` per event; set `parent_span_id` to the per-ticket `trace_id` (`${runId}:${t.id}`), or `null` where no parent is materialized — no `parentSpanId` argument threaded through the JS call chain | Satisfies the schema's two id fields with zero new call-graph plumbing; the ticket only requires the schema to *carry* the fields, and the downstream consumer (RUS-86) is signal/alerting, not trace-tree reconstruction (ref: Q3) | `parent_span_id` is a flat anchor, not a reconstructable nested span tree |
| B | Generate a `span_id` per event AND thread a real `parentSpanId` argument through `doDesign/doPlan → runPhase → emitEvent` to materialize a parent→child span hierarchy | A true nested trace tree | Threads a new argument through the JS control flow for a logging ticket; research Q3 confirms no span hierarchy exists and a parent linkage "must be threaded manually through the call chain" — added plumbing with no consumer that needs it |

**Recommendation:** Option A.
**Rationale:** The ticket requires the schema to **carry** `span_id`/`parent_span_id` (ref: ticket Standard event schema), not to reconstruct a trace tree — the only named downstream consumer, RUS-86, is signal-based monitoring/alerting (ref: ticket Dependent tickets), which needs correlatable ids, not parent→child nesting. Threading a `parentSpanId` through `doDesign/doPlan → runPhase` (the materialized-hierarchy approach) is unjustified call-graph complexity for a logging ticket when the per-ticket `trace_id` already supplies a correct, stable parent anchor (ref: Q3). A generated `span_id` keeps each event individually addressable; `parent_span_id = trace_id` keeps all of a ticket-run's events correlatable; `null` is used where no parent is materialized. If a future ticket genuinely needs a nested span tree, the threading can be added then — it is a non-breaking schema-compatible extension.
**NEW PATTERN?** No — reuses the generated-id + existing-`runId`-correlation approach (ref: Q3) with no new call-chain argument.

### Decision 6: `build_event` purity vs. the `timestamp` source

| Option | Approach | Pros | Cons |
|--------|----------|------|------|
| A | Make `build_event(*, timestamp, ...)` take the timestamp as a required argument (reads NO clock → genuinely pure); the I/O `append_event` supplies a `time.time()` default when the caller passed none, then calls `build_event` | `build_event` is deterministic and unit-testable with a fixed injected `timestamp` against tempfile roots (the pure-helper/IO-main split research Q12 makes load-bearing); the clock lives in I/O where it belongs | Caller (or `append_event`) must explicitly source the timestamp |
| B | Let `build_event` read the wall clock (`time.time()`) internally | One fewer argument | NOT pure — output varies by call time, so it cannot be the deterministically unit-testable assembler the design and Q12's convention require; contradicts listing it among the `pure helpers` |

**Recommendation:** Option A.
**Rationale:** A function that reads the wall clock is not pure (its output varies by call time), so the prior design's two assertions — `build_event` is a `pure` helper AND it stamps a `time`-derived timestamp — were contradictory. Option A resolves it by injecting `timestamp` into a genuinely-pure `build_event` and reading the clock only in the I/O layer (`append_event` defaults it via `time.time()` when the JS emitter did not pass an explicit value). This preserves the pure-helper/IO-`main` split that the stdlib unit-test convention depends on (ref: Q12): `qrspi_obs_test.py` exercises `build_event` with a fixed injected `timestamp` and asserts a byte-stable line, while the clock-reading I/O path is left to the same manual-e2e treatment as every other subprocess/IO `main` (ref: Q12). The JS emitter MAY also inject an explicit timestamp argument; either way `build_event` never reads a clock.
**NEW PATTERN?** No — this IS the established pure-helper/thin-IO-main split (ref: Q12), applied correctly.

### Decision 7: Where the ticket's `error_code` attribute lives in the schema

| Option | Approach | Pros | Cons |
|--------|----------|------|------|
| A | Map `error_code` into the optional `context` map on error/retry events (`context.error_code`), sourced from the failing `qrspi_*.py` envelope's `error` string / exit-code-mirrored failure and the JS `errored` marker (ref: Q2) | Uses the schema's existing `context` (defined "optional key-value metadata") with no schema widening; error code only appears where it is meaningful (error/retry events); sources from a real existing signal (every envelope carries an `error` string on failure, ref: Q2) | `error_code` is not a top-level field |
| B | Add a 13th top-level schema field `error_code` | Top-level prominence | Widens the ticket's named 12-field schema; the field is null for every non-error event |

**Recommendation:** Option A.
**Rationale:** The ticket's *Standard event schema* enumerates exactly 12 fields and does NOT name `error_code` among them — `error_code` is named only under *Error and retry tracking* ("the failure message, error code, and backoff duration"). The schema already provides `context` as "optional key-value metadata," which is the designated home for attributes that apply to a subset of events. Mapping `error_code` into `context.error_code` on error/retry events satisfies the *Error and retry tracking* criterion without widening the 12-field schema and without inventing a field that would be null on every successful transition. The source is real: every `scripts/qrspi_*.py` envelope carries an `error` string mirrored in its exit code on failure, and the JS dispatch records `action: 'errored'` (ref: Q2) — so the emitter has an authoritative code/message to record. This closes the prior gap where `error_code` vanished from the design with neither a mapping nor a deferral.
**NEW PATTERN?** No — reuses the existing `context` optional-metadata field and the existing envelope `error`/exit-code failure signal (ref: Q2).

### Decision 8: How per-command CLI structured logging is installed (the ticket's "Structured logging in the CLI" scope item)

The ticket names a scope item distinct from the phase-gate event log: **all qrspi CLI commands emit structured JSON logs to a file and optionally to stderr; log level is configurable; log context always includes ticket ID, phase, and trace ID.** Research Q6 is load-bearing here: there is **no shared CLI entry/wrapper** — every `scripts/qrspi_*.py` is standalone with its own `main()`/argparse — so this behavior "would have to be installed per-command or via a new shared module imported the `qrspi_paths` way." Leaving this as foundation-only (a `qrspi_obs.py` module nobody calls from the commands) would silently narrow the scope item, so this decision commits to the per-command retrofit.

| Option | Approach | Pros | Cons |
|--------|----------|------|------|
| A | **Per-command retrofit via the shared module.** Add `get_logger(...)`/`cli_log_record(...)` to `qrspi_obs.py`; each `scripts/qrspi_*.py` `main()` imports it and constructs a logger with the command's ticket/phase/trace context, emitting start + outcome `cli_log` records to the shared `events.jsonl` + optional stderr | Directly satisfies "all commands emit"; the mandatory ticket/phase/trace context is constructed once per command from args + `QRSPI_RUN_ID`; reuses the single events sink, lock, rotation, and config resolver already designed; honors stdout-reserved (ref: Q6, Q13); the pure record-builder is unit-testable (ref: Q12) | Touches every command's `main()` (a uniform ~3-line snippet + one import); a future new command must remember the snippet (no wrapper to enforce it) |
| B | **New shared CLI wrapper/entrypoint** all commands are refactored to route through | One install point; future commands inherit logging | Q6 found no such wrapper exists; building one is a large refactor of every command's argparse/main contract — out of scope for a logging ticket, and risks the stdout-envelope contract every worker depends on |
| C | **Defer the scope item** (event log only this ticket; CLI command logging in a follow-up) | Smaller blast radius | Silently drops a named ticket acceptance criterion unless explicitly deferred with rationale; the foundation (`qrspi_obs.py`) is already being built, so the marginal cost of the per-command snippet is small |

**Recommendation:** Option A — per-command retrofit through the shared module.
**Rationale:** The ticket requires **all** CLI commands to emit structured logs with always-present ticket/phase/trace context; Q6 proves there is no wrapper to install this once, so per-command installation is the only faithful path short of a large refactor (Option B). Option A reuses everything this design already builds — the `events.jsonl` sink (the "to a file" destination), the file lock, rotation/retention, and the typed `observability` config level — and adds only a uniform small snippet to each `main()` plus two pure helpers (`cli_log_record` is the testable surface). Routing the CLI logs into the **same** `events.jsonl` (with `event_type="cli_log"`, `actor=<command>`) keeps one queryable trace for RUS-86 rather than a second uncorrelated file, and the shared `trace_id` shape (`${QRSPI_RUN_ID}:${ticket}`) makes a command's log lines correlatable with the orchestrator's phase events. Deferral (Option C) is rejected because the foundation is already in this ticket; deferring would leave a named criterion delivered as foundation-only.
**NEW PATTERN?** Partly — the *logger* reuses the `qrspi_obs` writer + config-resolver patterns (not new), but a per-command structured-log snippet in every command's `main()` is a new convention (justified: Q6 found no wrapper to centralize it, and the per-command install is exactly what Q6's resolution prescribes).

## Risk Register

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|------------|
| Concurrent qrspi-batch runs interleave/corrupt the shared `events.jsonl` (ref: Q9) | med | high | `fcntl.flock` exclusive lock + single `os.write` of one `\n`-terminated blob under PIPE_BUF; writer fails closed if the lock cannot be taken |
| Crash mid-append leaves a torn final line no reader tolerates (ref: Q10) | med | med | One-line-per-`os.write` so a crash truncates only the last line; document that readers must drop a non-parseable trailing line; RUS-86 consumers follow suit |
| Per-transition worker spawn for emit adds latency / noise to every phase (ref: Q1) | high | low | Emit is best-effort and fire-and-forget: a failed `emitEvent` logs and never blocks `runPhase`'s boolean (mirrors metrics-append best-effort, ref: Q2) |
| Schema requires `backoff duration` that does not exist in the pipeline (ref: Q7) | high | med | Explicitly defer the backoff attribute with a documented note (no policy exists, ref: Q7); record the real `CI-Revise-Attempt` counter + `ciReviseCap` + `error_code` (from the envelope `error` string, ref: Q2) into `context` instead; surfaced as OQ1 |
| Rotation boundary races an in-flight writer / overshoots size cap (ref: Q11) | med | med | Rotate under the same append lock (Decision 3A); accept bounded overshoot of one record; unit-test `should_rotate`/`archive_name` against temp roots |
| `crypto.randomUUID` absent in the sandbox breaks id generation (ref: Q3) | low | med | Fall back to `crypto.getRandomValues` hex (the existing `runId` fallback ladder), never `Date.now()`/`Math.random()` |
| Per-command CLI-logging retrofit (Decision 8) is uneven — a command emits to stdout by mistake and corrupts the JSON envelope, or a future command forgets the snippet (no wrapper to enforce it, ref: Q6) | med | med | The `get_logger` default `stream=sys.stderr` makes stdout-corruption opt-in-only; the snippet is a single copy-pasted block + one import (uniform across commands); `qrspi_obs_test.py` asserts `cli_log_record` always carries ticket/phase/trace and never targets stdout; a missed snippet degrades gracefully (that command simply has no CLI log line — the phase-gate event still fires from the orchestrator) |

## Open Questions

- OQ1: Of the three *Error and retry tracking* attributes the ticket names (failure message, error code, backoff duration), two are designed in: the **failure message** is the schema `message` field on error/retry events, and the **error code** maps to `context.error_code` sourced from the failing envelope's `error` string (Decision 7, ref: Q2). Only **backoff duration** has no source: the ticket mandates a `backoff duration` field and an "exponential-backoff policy already defined in the pipeline config," but **no such policy or duration exists** (ref: Q7) — only the `ciReviseCap` count cap and fixed "retry once" prose. The design's decision is to **defer the backoff attribute** (omit/null it) and record the real attempt counter + cap instead; the open question is only whether to (a) keep that deferral with a documented note, (b) introduce a real backoff config as part of this ticket, or (c) split backoff into a follow-up ticket.
- OQ2: Rotation requires "compressed and archived" old files. Acceptable archive scheme — gzip in place to `events.<ISO>.jsonl.gz` beside the active file, or a separate `archive/` subdir? And is per-append size-check latency acceptable, or should rotation move entirely to the once-per-run invocation (Decision 3B)?
- OQ3: Should `trace_id` be `${runId}:${t.id}` (correlatable with the existing metrics ledger, ref: Q3) or a fresh per-ticket UUID? The former links the two structured sinks; the latter is opaque but simpler. (This is purely the `trace_id` *shape* — whether to materialize a nested parent→child span hierarchy is already settled in Decision 5: no, `parent_span_id` is the flat per-ticket `trace_id`, with no `parentSpanId` threaded through the JS call chain.)
- OQ4: Path shape (Decision 1) — confirm the single shared repo-root file is required despite breaking per-ticket isolation (ref: Q9), versus per-ticket files merged at query time.
