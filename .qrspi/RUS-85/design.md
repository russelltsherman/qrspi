# Design — Structured phase-gate event log (systematic logging)

**Ticket:** RUS-85
**Research basis:** research.md @ 2026-06-18T00:00:00Z
**Generated:** 2026-06-18T00:00:00Z
**Status:** draft

## Current State

The QRSPI review-gate pipeline runs phases through `runPhase(...)` in `.claude/workflows/qrspi-batch.js`, a boolean-returning function with no event emission, no status field, and no structured start/end signal — start is the de-facto `agent()` spawn, success is `return true` after the persist gate, and every failure is a `log(...)` line followed by `return false` (no exceptions thrown) (ref: Q1). There is no in-process retry inside `runPhase`; the only retry-shaped loop is the design-critic revise round loop, and transient `agent()` retry was deliberately withdrawn so a failed unit is recomputed on re-run rather than retried (ref: Q1).

Each phase already has `ticket_id` in scope as the `id`/`t.id` string and "phase" available in three distinct vocabularies — the `runPhase` artifact `name`, the harness UI `phaseLabel`, and the resolver `decision.phase` — but there is **no `actor` (agent vs user) discriminator anywhere**; the system models runs and workers, not human-vs-agent authorship (ref: Q2). A per-run correlation id, `runId`, already exists (crypto-derived, never timestamp-based, forbidden from using `Date.now()`/`Math.random()`), is threaded into the metrics ledger as `runId`, and is the natural `trace_id`; there is no per-phase `span_id` today (ref: Q3).

All self-locating scripts (`qrspi_resolve.py`, `qrspi_persist.py`, `qrspi_metrics_append.py`) share one rigid convention: `ENGINE_ROOT` from `__file__` for sibling imports, `qrspi_paths.resolve_repo_root(cwd=os.getcwd())` (git-common-dir-first → MAIN checkout root) for the host root, an argparse short-token CLI where the script owns every `qrspi`-laden path, a single `{ ok, ..., error? }` JSON envelope on stdout (indent=2 + trailing newline), and fail-once-never-retry semantics (ref: Q4). Config is read by `qrspi_config.py`, which reads exactly **one flat top-level key — no dot-path / nested support**; typed/numeric keys (like `ciReviseCap`) are read as a flat dict in Python then coerced in a pure helper, and any value surfaced through the JS envelope path must be a string (ref: Q5).

The per-ticket artifact dir `.worktrees/<id>/.qrspi/<id>/` is computed off the resolved host root and created lazily via `os.makedirs(dirname, exist_ok=True)` on first write; there is no eager provisioning step. `.qrspi/observability/` **does not exist** and must be added new, but the mechanism is fully analogous (ref: Q6). There is **no exponential-backoff policy in the pipeline config** — the only retry bound is a consecutive-failure *count* cap (`ciReviseCap`, default 3) with no inter-attempt interval; the only exponential backoff in the repo is `grade.py`'s LLM-judge retry, which is outside the QRSPI pipeline path (ref: Q7).

Within a single batch run, tickets are processed strictly sequentially (`for` loop with `await`), and isolation is per-worktree, so the existing per-ticket JSONL ledger is never contended; but the project explicitly supports multiple `qrspi-batch`/`qrspi-work` *processes* running concurrently on different tickets, each with its own `runId` (ref: Q8). A crash mid-phase persists nothing (the staging-then-move gate runs only after all stages pass), and the JSONL append pattern uses `open(path,"a")` + a single `json.dumps(line)+"\n"` write with **no fsync, no per-line checksum, and no lock** — append mode never rewrites prior lines, but a crash during a write can leave a trailing torn line that readers must tolerate (ref: Q9). The deliberate I/O split is fail-loud (`ok:false` + exit 1, once) for the success path versus degrade-silently-to-default for auxiliary config/reviewer reads (ref: Q10).

Tests are stdlib-`unittest` only, one `scripts/<name>_test.py` sibling per script, auto-discovered by `run_tests.py` (zero registration), with file-writing scripts tested against `tempfile.TemporaryDirectory()` roots and a monkeypatched `qrspi_paths.resolve_repo_root` (ref: Q11). `qrspi-batch.js` is not unit-testable in isolation; the law is Functional Core / Imperative Shell — deterministic logic lives in tested Python, the JS shell only shells out — verified via a syntax gate plus JS↔Python contract fixtures (ref: Q12). Three output channels coexist today, none structured: the human `log()` narration (81 free-form sites), the single-JSON-envelope stdout (reserved — the JS brace-scanner extracts the first balanced `{...}`), and stderr for a few harness scripts; the only structured line-oriented sink is the `critic-metrics.jsonl` ledger written by `qrspi_metrics_append.py`, which wraps each record with injected `ticketId` + UTC ISO-8601 `timestamp` (generated at write time in Python) + `runId` (ref: Q13, Q14). Per-ticket batch results live in an ephemeral in-memory `results` array; **phase durations are not recorded anywhere** (ref: Q14).

## Desired End State

A new Python emitter script appends one structured JSON event per phase-gate transition to a per-ticket JSONL event log, cloning the proven `qrspi_metrics_append.py` mechanics, with `qrspi-batch.js` firing it fire-and-forget at the hook points in `runPhase`.

- **AC "every phase transition produces a structured event (start, end, success, failure, retry)":** `runPhase` fires the emitter at four hook points identified in research — the `existing[name]` reuse/skip branch, immediately after entry (start), each `return false` site (failure), and just before `return true` (success) (ref: Q1). "Retry" maps to the only real retry surface — the CI-revise pass in the orchestrator's `doRevise` path — emitted there, not inside `runPhase` (ref: Q1, Q7).
- **AC "appended to a single JSONL file, append-only, append-aligned, never rewritten (crash-safe)":** events are appended via `open(...,"a")` + single `json.dumps(line)+"\n"` write (append mode never rewrites prior lines); the honest crash-safety bound is "prior lines never rewritten; a trailing torn line is possible," so readers tolerate a partial final line. See Open Questions for the single-file-vs-per-ticket layout decision (ref: Q9, Q8).
- **AC "standard event schema (event_id, trace_id, span_id, parent_span_id, timestamp, event_type, ticket_id, phase, actor, status, message, context)":** the emitter wraps each record with injected `ticket_id`, `timestamp` (Python UTC ISO-8601 at write time), and `trace_id` = `runId`; `event_id`/`span_id` are crypto-derived in Python (never `Date.now()`); `phase` uses the `runPhase` `name`/`decision.phase` vocabulary, not `phaseLabel`; `actor` is a new caller-supplied field defaulting to `agent` (ref: Q2, Q3, Q14). See Open Questions for `span_id`/`parent_span_id` semantics.
- **AC "error and retry tracking (failure message, error code, backoff duration)":** failure/retry events carry the failure message and an error code in `context`. **Backoff duration has no pipeline-config source of truth** — the pipeline bounds retries by a count cap, not an interval (ref: Q7); see Open Questions.
- **AC "log rotation and retention (configurable size default 10 MB, retention default 30 days, compress + archive old files)":** rotation/retention/level are flat top-level config keys (`logRotateBytes`, `logRetentionDays`, `logLevel`) read by `qrspi_config.read_config` + a `coerce_*` helper, never a nested block (ref: Q5). The full size→archive→retention pipeline runs **synchronously in Python at append time**, immediately after the event line is written, inside `qrspi_event_append.py` (the same self-locating script, so no separate scheduler/cron is introduced — there is no daemon in this system, ref: Q1, Q6):
  1. **Rotate (size):** after the append, the script reads `os.path.getsize(events.jsonl)`; if it exceeds `logRotateBytes` (default `10485760`, coerced by `coerce_bytes`; `0`/negative/non-int → default, never "disabled silently"), the active file is rotated.
  2. **Compress + archive:** the rotated file is renamed to a timestamped archive name and gzip-compressed via stdlib `gzip` into an **`archive/` sub-directory beside the active log** — `<active-log-dir>/archive/events-<UTC-ISO-compact>.jsonl.gz` (with the per-ticket layout of Decision 1, that is `.worktrees/<id>/.qrspi/<id>/archive/`). The archive timestamp is generated in Python at write time (`datetime.now(timezone.utc)`), never in JS (ref: Q3, Q14). A fresh empty `events.jsonl` then continues receiving appends.
  3. **Enforce retention (purge):** in the **same append-time pass**, the script scans `<active-log-dir>/archive/*.jsonl.gz` and **deletes** any archive whose age exceeds `logRetentionDays` (default `30`, coerced by `coerce_days`). Age is computed from the archive's own filename timestamp (the authoritative, tz-safe source — `os.stat` mtime is a fallback only if the name is unparseable), compared against the Python-generated "now". This is the concrete actor + mechanism + location + trigger the retention AC requires: **`qrspi_event_append.py` purges, at every append, archives older than the configured window from the `archive/` dir.**

  This "do it inline at append time" choice deliberately mirrors how the pipeline already bounds the CI-revise loop — there is **no separate scheduled job anywhere** in the codebase (the only retry/sweep surfaces are inline, append-time/decision-time, ref: Q1, Q7), so a separate retention cron/daemon would be a brand-new infrastructure pattern with no precedent. Retention enforcement is **best-effort/degrade** like the emit itself: a failed unlink/rotate must NOT crash a phase (logging is auxiliary, ref: Q10), but is reported honestly in the emitter's own `ok:false` envelope. See Decision 4 for the alternatives weighed.
- **AC "structured logging in the CLI (JSON to file, optional stderr, configurable level, context always includes ticket/phase/trace):** a shared Python logging helper emits structured JSON to a log file and optionally stderr, gated by `logLevel`, with every line carrying ticket_id, phase, and trace_id; it must NOT write extra JSON to a script's stdout (reserved for the result envelope) (ref: Q13).

## Delta

- **New file `scripts/qrspi_event_append.py`** — self-locating emitter (mirrors `qrspi_metrics_append.py`): argparse short tokens (`--ticket`, `--run-id`, `--phase`, `--event-type`, `--status`, `--actor`, `--message`, `--context`, `--repo-root`), computes the canonical event-log path, wraps + appends one event line, then runs the **inline rotation → gzip-archive → retention-purge pass** (Decision 4) in this order: append → if `size > logRotateBytes` rotate the active file to `archive/events-<UTC>.jsonl.gz` (stdlib `gzip`) → scan `archive/*.jsonl.gz` and unlink any whose filename-timestamp age exceeds `logRetentionDays`. Emits one `{ ok, ..., error? }` envelope. Best-effort: a write/rotate/purge failure must NOT crash a phase (degrade), but reports `ok:false` honestly (ref: Q4, Q6, Q10). The size/age comparisons use **pure helpers** (`should_rotate(size, limit)`, `is_expired(archive_name, now, days)`) so the rotation/retention decision is unit-testable without touching the filesystem (Q11 split: pure logic + I/O against a temp dir).
- **New file `scripts/qrspi_event_append_test.py`** — clones `qrspi_metrics_append_test.py` (temp dir + monkeypatched `resolve_repo_root`); asserts append-not-overwrite, schema-field injection, `trace_id`=`runId` round-trip, rotation trigger (file over `logRotateBytes` produces an `archive/*.jsonl.gz` and a fresh empty active file), **retention purge** (a planted archive whose filename timestamp is older than `logRetentionDays` is deleted while an in-window archive survives — driven by injecting "now", no `sleep`), the pure `should_rotate`/`is_expired` helpers with literal args, and torn-trailing-line tolerance (ref: Q11). Auto-discovered by `run_tests.py`.
- **New file `scripts/qrspi_log.py` (+ `_test.py`)** — shared structured-JSON CLI logging helper (level gate, file + optional stderr, mandatory ticket/phase/trace context).
- **New helper in `scripts/qrspi_config.py` usage** — `coerce_bytes` (default `10485760`) / `coerce_days` (default `30`) pure helpers (pattern of `coerce_cap`: read the flat key via `read_config`, coerce to a positive int, reject `bool`/non-int/non-positive → default — so `select_value`'s `0`-as-absent trap is avoided, ref: Q5). `coerce_days` feeds the retention purge; `coerce_bytes` feeds the rotation trigger. Both live in / are called from `qrspi_event_append.py` (it owns the rotation+retention decision), reading `.qrspi/config.json` through `qrspi_config.read_config`.
- **Modified `.claude/workflows/qrspi-batch.js`** — minimal: fire-and-forget shell-out to `qrspi_event_append.py` at the four `runPhase` hook points and at the `doRevise` retry site, using `engineCmd(...)` + existing `runId`/`id` in scope (no new JS logic — Functional Core law) (ref: Q1, Q12).
- **Modified `.qrspi/config.example.json`** — document `logRotateBytes` (10485760), `logRetentionDays` (30), `logLevel` ("info"), each as a flat key, with a `$comment` noting `logRetentionDays` drives the append-time archive purge in `qrspi_event_append.py` and `logRotateBytes` the gzip-rotation trigger (ref: Q5).
- **No contract-fixture seam** unless JS must parse the emitter envelope; the precedent (`qrspi_metrics_append.py` at :995) is fire-and-forget with no JS parse, so only the syntax gate covers the JS edit (ref: Q12).

## Pattern Decisions

### Decision 1: Event-log file layout (single shared file vs per-ticket)

| Option | Approach | Pros | Cons |
|--------|----------|------|------|
| A | Single shared `.qrspi/observability/events.jsonl` at repo root | Matches ticket wording; one queryable stream | First cross-ticket shared sink; breaks per-worktree isolation; concurrent appends risk torn lines with no lock (ref: Q8) |
| B | Per-ticket `.worktrees/<id>/.qrspi/<id>/events.jsonl` | Matches existing ledger layout exactly; never contended; clones working precedent (ref: Q6, Q8) | Diverges from ticket's literal "single file"; a query step must concatenate per-ticket files |

**Recommendation:** Option B
**Rationale:** The existing durable JSONL ledger (`critic-metrics.jsonl`) is per-ticket-per-worktree and never contended; the lock-free `open(...,"a")` pattern is unsafe for concurrent cross-process writers, and a single repo-root file would be the system's first shared sink, breaking the per-worktree isolation invariant (ref: Q6, Q8). B clones the proven pattern wholesale. The ticket's "single JSONL file" intent is preserved by treating per-ticket files as the durable source and offering a concatenating reader (a concern for RUS-86, the monitoring layer). **This contradicts the ticket's literal path** — see OQ1.
**NEW PATTERN?** No — clones `qrspi_metrics_append.py`'s per-ticket append-only JSONL ledger.

### Decision 2: Where event emission lives (Python emitter vs inline JS)

| Option | Approach | Pros | Cons |
|--------|----------|------|------|
| A | New Python `qrspi_event_append.py`, JS fires fire-and-forget | Obeys Functional Core law; fully unit-testable; timestamp/crypto-id in Python; reuses self-locating convention (ref: Q4, Q11, Q12) | One subprocess per event |
| B | Inline event-building in `qrspi-batch.js` | No subprocess | Forbidden by the architectural law; not unit-testable; can't use `Date.now()`/`Math.random()` for ids/timestamps (ref: Q3, Q12) |

**Recommendation:** Option A
**Rationale:** Functional Core / Imperative Shell is "the single strongest constraint on RUS-85's shape" — deterministic logic must be tested Python; timestamps and ids must originate in Python because the JS shell forbids `Date.now()`/`Math.random()` (ref: Q3, Q12). A directly reuses the established emitter precedent.
**NEW PATTERN?** No.

### Decision 3: Failure handling for the emitter (fail-loud vs degrade)

| Option | Approach | Pros | Cons |
|--------|----------|------|------|
| A | Degrade: a log-write failure never stops a phase; emitter reports `ok:false` to its own stdout but JS ignores it | Logging is auxiliary — never break the pipeline for observability (ref: Q10) | A lost event is silent to the operator |
| B | Fail-loud: a log-write failure returns false from `runPhase` | Strong "no missing events" guarantee | A logging fault would halt real work — inverts priorities; contradicts auxiliary-read precedent (ref: Q10) |

**Recommendation:** Option A
**Rationale:** The deliberate split is fail-loud for the *success path* (artifact persist) and degrade-silently for *auxiliary* reads (config/reviewers); observability is auxiliary, so the emit must not crash a phase, while its own self-test reports `ok:false` honestly (ref: Q10). The JS fires it fire-and-forget like the metrics append (ref: Q12).
**NEW PATTERN?** No.

### Decision 4: Retention enforcement — where/when archives are purged

The rotation AC has three sub-behaviors: trigger at size, compress+archive, and **enforce a retention window by deleting old archives**. The first two have a clear home (append-time check + stdlib `gzip`); the third needs an explicit actor, trigger, and location decision — this is the gap the panel flagged.

| Option | Approach | Pros | Cons |
|--------|----------|------|------|
| A | Inline at append time inside `qrspi_event_append.py`: after every append, rotate-if-needed, then scan the `archive/` dir and unlink archives older than `logRetentionDays` | No new infrastructure — there is **no scheduler/daemon/cron anywhere** in the system (ref: Q1, Q7); reuses the established self-locating + best-effort-degrade + pure-helper conventions; the actor/trigger/location are concrete and unit-testable | Purge cost is paid on the append that crosses a rotation; an append-only-when-active log means very old archives are only reaped once a new event arrives (acceptable — the ticket asks for a retention window, not a real-time reaper) |
| B | A separate scheduled job / cron that periodically sweeps archives | Decouples purge from the hot path | **No scheduler exists** — would be the first cron/daemon in the codebase, a brand-new infra pattern with no precedent, contradicting the "everything is inline at append/decision time" shape (ref: Q1, Q7) |
| C | Purge only at rotation time (not every append) | Slightly cheaper | A log that never grows past `logRotateBytes` would never rotate and therefore never purge — old archives could outlive the window indefinitely; weaker guarantee |

**Recommendation:** Option A
**Rationale:** The system has no daemon/scheduler surface (the only retry/sweep mechanisms — the CI-revise cap, the resume recompute — are all inline at append/decision time, ref: Q1, Q7), so a cron (Option B) would be net-new infrastructure with no precedent. Doing the purge inline at append time (A) gives the retention AC a concrete actor (`qrspi_event_append.py`), trigger (every append, after the size/rotate check), and location (the `archive/` sub-dir beside the active log), all inside the same best-effort, fail-degrade, unit-testable Python the rest of RUS-85 uses. Scanning the whole `archive/` dir on every append (not only at rotation, rejecting C) guarantees a stale archive is reaped on the next event regardless of whether a rotation happened on that append.
**Archive location:** `<active-log-dir>/archive/events-<UTC-ISO-compact>.jsonl.gz` — for the per-ticket layout chosen in Decision 1, that resolves to `.worktrees/<id>/.qrspi/<id>/archive/`, created lazily with `os.makedirs(..., exist_ok=True)` exactly like the active log dir (ref: Q6). Keeping archives in a sub-dir (not alongside the active `events.jsonl`) makes the retention scan a simple glob and keeps the active append target unambiguous.
**Age source:** the archive **filename timestamp** (Python-generated at rotation, ISO/UTC) is authoritative for `is_expired`; `os.stat` mtime is a fallback only when a name is unparseable — this keeps age computation tz-safe and independent of filesystem clock quirks.
**NEW PATTERN?** Partly — the `archive/` sub-dir and the inline rotate+purge pass are new (no log file has ever rotated before), but they are built entirely from existing conventions (self-locating script, lazy `os.makedirs`, stdlib `gzip`, pure coercion helpers, best-effort degrade). No new scheduler or daemon is introduced.

## Open Questions

- OQ1: The ticket specifies a **single** `.qrspi/observability/events.jsonl`, but the codebase precedent and concurrency safety argue for **per-ticket** files (Decision 1). Accept per-ticket files with a concatenating reader, or invest in a lock/atomic-append for a true single shared file? (ref: Q6, Q8)
- OQ2: The ticket says retry intervals "follow the exponential-backoff policy already defined in the pipeline config," but **no such policy exists** — the pipeline bounds retries by a count cap (`ciReviseCap`), not an interval (ref: Q7). Should we (a) emit the attempt-count instead of a backoff duration, (b) define a new backoff config now, or (c) drop the backoff-duration field? This blocks the "backoff duration" part of the error/retry AC.
- OQ3: `actor` (agent vs user) has no model in the system (ref: Q2). Is a static `actor=agent` for all autonomous pipeline events acceptable for RUS-85, deferring a real human-vs-agent distinction to a later ticket?
- OQ4: `span_id` / `parent_span_id` have no precedent (`runId` is the only id today, ref: Q3). What is the intended span hierarchy — one span per phase under the run as parent, or finer-grained? This determines how ids are generated and threaded.
- OQ5: Is phase **duration** in scope for RUS-85? No timing exists today and pairing start/end timestamps into a duration is new work (ref: Q14). If yes, the emitter must correlate a start event's timestamp with its end event.
