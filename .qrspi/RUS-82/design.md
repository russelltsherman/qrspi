# Design — Holistic design critic: adversarial node-validity lens with codebase access

## Current State

The design-phase critic is a four-lens panel — `completeness`, `internal-consistency`, `edge-alignment`, `simplicity` — fanned out in parallel by `runCriticPanelLoop(name, id, criticConfig)`, which threads exactly four path lines (`DESIGN_PATH`, `TICKET_CONTENT_PATH`, `RESEARCH_PATH`, `QUESTIONS_PATH`) plus an optional fifth `DIGEST_PATH` into every lens prompt; there is no repo/worktree root in scope inside the loop, though the worktree root `wd` is available at the `doDesign` call site where `criticConfig` is assembled (ref: Q1). The shared research digest (RUS-77 cost lever) is built once per step when `criticConfig.digest.enabled` is true; the digest is applied uniformly to every lens via a single `digestLine`, and the per-lens opt-out lives only in each lens agent's prompt instructions ("Read `DIGEST_PATH` in place of `RESEARCH_PATH`"), not in any loop-side per-lens flag (ref: Q2). Every lens emits the same `CRITIC_VERDICT_SCHEMA` shape — `{pass: boolean, findings: string[]}` — defined once in `qrspi-batch.js` and used as the runner-boundary validator, with a fail-closed Python coercion backstop (ref: Q3).

All four lens agent files declare identical frontmatter with `claude.tools: Read` (Read only — no Grep, no Bash) and no model key; the proven format to grant Read+Grep is the comma list `tools: Read, Grep`, and the per-lens model override is a runtime `agent()` option fed from `criticConfig.lensModel` (a documented-possibly-inert seam) rather than frontmatter (ref: Q4). `DEFAULT_DESIGN_LENSES` is duplicated in `qrspi-batch.js` and `scripts/qrspi_critics_config.py` (Python is the tested source of truth); `KNOWN_DESIGN_LENSES = set(DEFAULT_DESIGN_LENSES)` exists only in Python — i.e. the whitelist is currently *defined as* the default-active set, so the two are not yet decoupled — and `resolve_design` drops any config lens id not in that whitelist with a warning, falling back to the full default four when the resolved set is empty — so a new lens id is silently dropped unless it is in the whitelist (ref: Q5). `scripts/qrspi_critic_synthesize.py` AND-reduces over whatever verdict list it is handed (pass only if non-empty and every lens passed); it knows no "expected set" — membership is enforced upstream by the JS fan-out over `criticConfig.lenses`, where a failed-spawn lens aborts the ticket before synthesize runs (ref: Q6).

When unanimity is never reached the loop ships via `cap_reached` after `maxRounds` (default 2), carrying residual findings into the PR body — a perpetually-dissenting lens does not block, it caps out and ships; only an infrastructure abort (`ok:false`) stops a ticket (ref: Q7). A null/missing verdict aborts the ticket (fail-closed, never silent-pass) and a malformed-but-present verdict reads as fail; nothing fails open (ref: Q8). The panel is hard-keyed to "design" in four spots — the `qrspi-design-critic-${lens}` agentType prefix, the "design-phase critic panel" / "judge `DESIGN_PATH`" prompt text, the design-keyed input var names (`DESIGN_PATH`, `RESEARCH_PATH`, `TICKET_CONTENT_PATH`, `QUESTIONS_PATH`), and each agent file's prose — while the loop control structure (round loop, fan-out, synthesize, `next_action`, metrics) is already phase-agnostic, and the single-critic `runCriticLoop` already demonstrates phase-generic `UPSTREAM_PATH`/`ARTIFACT_PATH` naming (ref: Q9). Tests are stdlib-only `unittest` `<module>_test.py` files discovered by `run_tests.py`; `qrspi_critics_config_test.py` asserts whitelist keep/drop behavior and `qrspi_critic_synthesize_test.py` asserts the reduced verdict (ref: Q10). The teeth eval feeds the real panel a flawed `evals/teeth/design.md` with one marker per owning lens (`completeness`, `internal-consistency`, `edge-alignment` only — `simplicity` is uncovered), asserting a 2-of-3 majority catch via `scripts/qrspi_teeth_assert.py::evaluate` (ref: Q11). Per-lens output flows to a `log()` aggregate and a durable `CriticStepMetrics` ledger (`{lens, pass, findingsCount}` per round) with no blocking-vs-non-blocking dimension — every lens is equally blocking under the AND-reduce (ref: Q12).

## Desired End State

- **AC1 (node-validity lens exists):** A new agent `.claude/agents/qrspi-design-critic-design-review.md` judges the NODE — architectural soundness, correctness, failure modes, edge cases, operability, testability, security/perf, alternatives not considered — framed as "find what is materially wrong," emitting the standard `{pass, findings}` verdict (ref: Q3, Q4).
- **AC2 (codebase access, read-only):** The lens declares `tools: Read, Grep` in frontmatter and receives a `CODEBASE_PATH` line threaded by `runCriticPanelLoop`; it reads source to verify at least one design claim — **demonstrated by the AC5 codebase-claim teeth defect, which is catchable only by reading source**. `Bash` is not granted (no concrete read-only-probe need is shown). The other four lenses stay `Read`-only (ref: Q1, Q4).
- **AC3 (wired into the panel, DEFAULT-OFF):** `design-review` is added to a `KNOWN_DESIGN_LENSES` whitelist that is **decoupled from** the default-active `DEFAULT_DESIGN_LENSES` set (it is NOT appended to `DEFAULT_DESIGN_LENSES`). The lens is therefore whitelist-accepted but **inactive by default**; it activates only when a config author lists `design-review` in `critics.design.lenses`. When activated it is AND-reduced by the unchanged synthesize reducer (ref: Q5, Q6). This is the concrete realization of the ticket's mandatory default-OFF / opt-in Constraint (see Decision 2).
- **AC4 (severity bar):** The lens fails only on material/blocking defects, and `findings` is **blocking-only** — `pass:false` ⟺ `findings` non-empty (a sound-but-imperfect design returns `pass:true, findings:[]`; stylistic observations are NOT emitted as structured findings — they may appear in the agent's free-text return, which is not scored). This lets the strict-unanimity panel converge while keeping `findingsCount` a clean blocking signal that does not pollute the dissent metric (see Decision 4) (ref: Q6, Q7).
- **AC5 (teeth on a node defect):** A new labelled node-defect — specifically an **unverifiable codebase claim** (a design assertion about real source that is false, e.g. "extends helper `foo()` in `bar.py`" where no such symbol exists), NOT an unsound choice and NOT a dropped AC — plus its marker is added to `evals/teeth/design.md` and `LENS_MARKERS`, and the lens fails citing it. This is **also the AC2 demonstration** that the lens reads source: only a codebase-claim defect requires reading the repo to catch (an unsound choice is catchable by reasoning alone) (ref: Q11, AC2).
- **AC6 (no regression toward noise):** On a clean design the panel still converges without fabricated findings. Under Decision 4 Option B (blocking-only findings) this is trivially checkable: the node lens returns `pass:true, findings:[]` on a clean design, so `findingsCount` stays 0 and the verdict registers no dissent (ref: Q7, Q11).
- **AC7 (cost/model profile decided explicitly):** The lens opts out of the digest and reads full research + source. **Model: recorded as intent only** — target the strongest available model (Opus-tier) for this validity review — **NOT wired via `lensModel`**, because that seam is **panel-wide** (one value applied to every lens, `qrspi-batch.js:893`), so setting it would re-model the other four lenses too; a true per-lens override would restructure the loop (out of scope). The lens therefore inherits the panel's session model at runtime. The other four lenses keep their RUS-77 cost levers unchanged (ref: Q2, Q4; OQ1).
- **AC8 (unit tests):** Stdlib-only `_test.py` additions cover whitelist acceptance of `design-review`, the default lens set staying the four (default-OFF), opt-in activation, and synthesize handling of the extra lens, passing under `run_tests.py` (ref: Q10).

## Pattern Decisions

### Decision 1: How the new lens receives codebase access

| Option | Approach | Pros | Cons |
|--------|----------|------|------|
| A | `tools: Read, Grep` frontmatter + a `CODEBASE_PATH` prompt line spliced in `runCriticPanelLoop`, sourced from `wd` in `doDesign` | Matches the existing `ticketContentPath`/`questionsPath` plumbing pattern; read-only honors AC2; smallest wiring | Adds a path the loop applies to ALL lenses (others ignore it via prompt) |
| B | Also grant `Bash` (constrained non-mutating) | Enables richer probes (grep pipelines, file listing) | AC2 requires a concrete shown need; risks worktree mutation; larger trust surface |

**Recommendation:** Option A
**Rationale:** Threading a path through `criticConfig` mirrors how `ticketContentPath` and `questionsPath` are already passed from `doDesign` (where `wd` is in scope) into the loop prompt (ref: Q1). Granting Read+Grep uses the proven `tools: Read, Grep` format (ref: Q4). Bash is excluded because AC2 admits it only on a shown need. The spliced line uses the name `CODEBASE_PATH`, and the agent file consumes that same name — the two halves of the wiring share the identical variable name (no `ARTIFACT_PATH`/generic-upstream rename is introduced on the consuming side).
**NEW PATTERN?** Partial — threading a new config path is the established pattern (ref: Q1), but granting a lens any tool beyond `Read` reverses the standing "lenses are Read-only / do not explore the codebase" convention (ref: Q4). Justified: this lens's entire purpose (node validity against real source) is impossible Read-only.

### Decision 2: Default-OFF wiring — whitelist-accepted but not active-by-default

This decision exists specifically to satisfy the ticket Constraint: *"Default-OFF / opt-in posture consistent with the rest of the critic config; the lens activates only when listed in `critics.design.lenses`."* It is a mandatory constraint, stricter than AC3's permissive "in the default lens set (or config-addable)" phrasing, so the constraint governs and the lens MUST ship OFF by default.

| Option | Approach | Pros | Cons |
|--------|----------|------|------|
| A | Append `design-review` to `DEFAULT_DESIGN_LENSES` (which today *is* `KNOWN_DESIGN_LENSES`) | One-line edit; lens whitelist-accepted automatically | Makes the lens **active by default** — directly violates the default-OFF Constraint, since `KNOWN_DESIGN_LENSES = set(DEFAULT_DESIGN_LENSES)` means a single append both whitelists AND activates it (ref: Q5) |
| B | **Decouple** the whitelist from the default set: keep `DEFAULT_DESIGN_LENSES` as the four, redefine `KNOWN_DESIGN_LENSES = set(DEFAULT_DESIGN_LENSES) \| {"design-review"}` | Lens is whitelist-accepted (config can opt in) but **inactive by default**; honors the Constraint exactly; the resolver keeps the default four when `design-review` is not listed | Whitelist is no longer literally `set(DEFAULT_DESIGN_LENSES)` — a deliberate, documented decoupling; one extra symbol to keep in sync (Python only — JS has no whitelist constant) |

**Recommendation:** Option B
**Rationale:** Today `KNOWN_DESIGN_LENSES = set(DEFAULT_DESIGN_LENSES)` (ref: Q5), so appending to `DEFAULT_DESIGN_LENSES` (Option A) ships the lens ON by default — the exact opposite of the Constraint. Decoupling (Option B) makes "whitelist-acceptable" and "active-by-default" independent: `design-review` enters `KNOWN_DESIGN_LENSES` (so `resolve_design` keeps it when a config lists it) but stays out of `DEFAULT_DESIGN_LENSES` (so the default resolved set is still the four, and the empty-fallback still falls back to the four). The lens activates only when an author writes `"critics": {"design": {"lenses": [..., "design-review"]}}`, which is precisely the opt-in posture the Constraint mandates and matches the rest of the critic config's default-OFF vocabulary (ref: research "Uniform `enabled` vocabulary"). The JS `DEFAULT_DESIGN_LENSES` fallback also stays the four (it is the config-read-failure path; including `design-review` there would re-introduce default-ON on that path).
**NEW PATTERN?** Yes (small) — it introduces the first divergence between `KNOWN_DESIGN_LENSES` and `set(DEFAULT_DESIGN_LENSES)`. This is the minimal structural change that satisfies the default-OFF Constraint without restructuring the resolver or synthesize (both untouched). The decoupling is asserted by tests (default set unchanged; listed-`design-review` kept; unlisted-`design-review` absent).

### Decision 3: Where the `CODEBASE_PATH` line is consumed (one prompt vs per-lens)

| Option | Approach | Pros | Cons |
|--------|----------|------|------|
| A | Splice `CODEBASE_PATH` uniformly into every lens prompt; only `design-review` is instructed to use it | No per-lens branching in the loop; mirrors how `digestLine` is applied uniformly today | The four Read-only lenses see a path their tools can't act on (cosmetic) |
| B | Conditionally append the line only for the `design-review` lens | Cleaner prompts for the other four | Introduces the first per-lens prompt conditional; more JS surface; diverges from the uniform `digestLine` pattern |

**Recommendation:** Option A
**Rationale:** The digest line is already computed once and applied uniformly across `lenses.map(...)` with the per-lens use/ignore decision pushed into the agent prompt (ref: Q2). Reusing that same uniform-line + agent-side-decision shape keeps the loop free of per-lens conditionals and matches precedent. The "Read all four paths" wording must be corrected regardless (ref: Q1, and the noted inconsistency that it is already wrong-by-one when `DIGEST_PATH` is present).
**NEW PATTERN?** No — reuses the uniform-line pattern from the digest (ref: Q2).

### Decision 4: Convergence under strict unanimity (severity bar realization)

The severity bar lets the panel converge on a sound-but-imperfect design while still biting on material defects. The realization must respect a constraint the **dissent metric** imposes: `qrspi_critic_summary.py:146` records a round as dissent when `pass is False` **OR** `findingsCount > 0`. So *any* finding on a `pass:true` verdict registers as dissent and is indistinguishable from a real defect for AC6's noise check.

| Option | Approach | Pros | Cons |
|--------|----------|------|------|
| A (rejected) | Stylistic items go in `findings` with `pass:true` | Keeps advisory notes visible in structured output | **Every advisory note has `findingsCount > 0` → recorded as dissent**, polluting the RUS-78 base rate that RUS-79 consumes to judge leniency; and an advisory note becomes indistinguishable from a fabricated finding, making AC6 unverifiable |
| B (recommended) | **`findings` is blocking-only: `pass:false` ⟺ `findings` non-empty.** A sound design returns `pass:true, findings:[]`; stylistic observations are not emitted into the schema'd `findings` (they may appear in the agent's free-text return, which is not scored) | `findingsCount` stays a clean blocking signal; the dissent metric is not polluted; AC6 is trivially checkable (clean → `pass:true, []`); matches the family's "every `pass:false` MUST carry a finding" rule; **zero synthesize change** | Stylistic notes are not surfaced as structured findings (acceptable — they are non-blocking by definition) |
| C | Add a per-lens blocking flag to the verdict + change synthesize to exclude non-blocking lenses | Structural separation of advisory vs blocking | Constraint explicitly forbids restructuring the synthesize reducer; new field across verdict/metrics schema (ref: Q12) |

**Recommendation:** Option B
**Rationale:** Option A reads natural but breaks the measurement — a passing lens that emits advisory findings is logged as dissent (`is_dissent = is_pass_false or findingsCount > 0`), inflating the very base rate the RUS-77 family uses to judge leniency and collapsing AC4's "advisory note" into AC6's "fabricated finding." Option B keeps the bar entirely in the prompt (no synthesize change, honoring the constraint) but maps it to the schema cleanly: findings are reserved for material/blocking defects, so `pass` and `findingsCount` move together. C is barred (restructures synthesize) (ref: Q6, Q12).
**NEW PATTERN?** No — `{pass:false, [finding]}` and `{pass:true, []}` are the ordinary verdict shapes; the lens simply never emits a non-blocking finding (ref: Q3).

### Decision 5: Digest vs full-context for this lens (AC7)

| Option | Approach | Pros | Cons |
|--------|----------|------|------|
| A | Lens ignores `DIGEST_PATH`, always reads full `RESEARCH_PATH` + source | A code-reading validity review needs full context; preserves digest cost lever for the other four | Higher token cost for this one lens (intended) |
| B | Lens reads the digest like the others | Lower cost | Undercuts the node-validity purpose — the digest trims content a validity review needs |

**Recommendation:** Option A
**Rationale:** The per-lens digest decision already lives in the agent prompt, not the loop (ref: Q2), so this lens opting out is a one-line prompt instruction with no loop change. AC7 explicitly anticipates this lens legitimately differing; documenting "reads full research + source; other four keep the digest" satisfies the AC.
**NEW PATTERN?** No — the opt-out mechanism (agent prompt chooses `DIGEST_PATH` vs `RESEARCH_PATH`) already exists (ref: Q2).
