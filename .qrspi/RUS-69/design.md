# Design — Resolver mis-classifies partially-landed stacks as entry_blocked

**Ticket:** RUS-69
**Research basis:** research.md @ 2026-06-11T14:10:00Z
**Generated:** 2026-06-11T15:00:00Z
**Status:** revised (open questions resolved by review)

## Current State

The resolver `resolve(state)` is a pure function over a single normalized `state` dict built by `qrspi_pr_state.build_state(...)`; that dict carries `ticketId`, `assigned`, `linearStatus`, `blockedOpen`, `blockedBy`, and a `phases` map with fixed keys `design`, `plan`, `implementation` (ref: Q1). Each phase/slice PR dict already carries `merged`, `state`, and `mergedAt` alongside `prExists`, `reviewDecision`, `unresolvedThreads`, and `branchExists`, but the resolver reads NONE of the merge fields — it consults only `branchExists`, `prExists`, `reviewDecision`, `unresolvedThreads`, `commentTargets`, plus implementation's `expectedSlices`/`prSummaryCommitted`/`slices` (ref: Q1).

The gather step selects one PR node per head via `parse_pr_nodes(..., prefer="active")` (identity `nodes[0]`, newest by creation), surfacing `merged`/`state`/`mergedAt` on that node; the merge-aware aggregators `stack_merge_state`/`is_stack_fully_merged` exist but are consumed only by `qrspi_cleanup.py`, never by `build_state` (ref: Q2). A phase "exists" only when `phase_exists(phases, name)` is truthy, which equals `branchExists`, set by `build_state` via `real_branches` — a phase counts only if its branch appears in `git branch --list <ticket>/*` AND is ≥1 commit ahead of trunk (ref: Q7). This is purely LOCAL-branch presence and is blind to merge status; after a design PR merges, `gt sync --force` prunes the local branch, flipping `branchExists` to False so the ticket reads as "not started" (ref: Q7, Q2).

The resolver's first check is the entry gate: `if "design" not in existing` (ref: Q9). When the design branch is absent and the ticket is not `assigned + Selected`, it returns `entry_blocked` with reason "No design branch and ticket is not assigned+Selected; nothing begins."; if still `assigned + Selected` it returns `run_design`, which would RE-create design for an already-landed phase (ref: Q6, Q11). The entry gate inspects only `assigned`, `linearStatus`, `blockedOpen`, `blockedBy` — never any merge signal nor implementation slice presence — so a genuinely un-started ticket and a partially-landed ticket whose design branch was pruned are indistinguishable to it (ref: Q10). Because the entry gate runs FIRST and short-circuits, the open, approved upper slice branches are never examined (ref: Q9, Q10).

The action vocabulary is the `ACTIONS` tuple (`entry_blocked`, `run_design`, `submit`, `wait`, `revise`, `respond_comment`, `advance`, `land`, `reset`); there is no dedicated "finish landing remaining slices" action — `land` is all-or-nothing and reachable only while `active == "implementation"`, which itself requires the design/plan/impl phases to pass `real_branches` (ref: Q4, Q5). The batch orchestrator switches on `r.decision.action`; `entry_blocked` (and `wait`) fall through to `skip(...)`, treated as a benign terminal skip with no special-casing for stranded in-flight stacks (ref: Q8). The only diagnostic for a skipped ticket is the `reason` string surfaced in `results[].summary`; nothing flags that an `entry_blocked` ticket may actually be a partially-landed stack (ref: Q14).

Resolver tests in `qrspi_resolve_state_test.py` use builders `_phase`/`_slice`/`_impl`/`state` that set only branch/PR/decision/thread/comment fields; no builder accepts a `merged` argument, and no fixture models a merged-lower / open-upper stack — merge selection is tested only in `qrspi_pr_state_test.py`, which never flows into a `resolve()` assertion (ref: Q12, Q13).

## Desired End State

- **AC1** — A ticket whose design/plan PRs have merged (and whose lower branches were pruned) while one or more upper slice PRs remain open and approved resolves to an action that lands the remaining slices, not `entry_blocked`. The resolver gains a notion that the design phase is "started but already landed" so it bypasses the entry gate and reaches the implementation/land logic (ref: Q5, Q9, Q11).
- **AC2** — The resolver no longer emits the "No design branch" entry_blocked reason for a ticket whose design PR has already merged. When `phases.design.merged` (or the equivalent stack-level merge verdict) is true, design-branch absence is treated as already-landed rather than never-started (ref: Q6, Q11).
- **AC3** — A new resolver unit test reproduces the merged-lower / open-upper stack shape (design/plan merged-and-gone, slices open + APPROVED) that currently yields `entry_blocked`, asserting the new landing action instead. This requires extending the test builders with a merge dimension (ref: Q12, Q13).
- **Constraint (entry gate preserved)** — A truly un-started ticket (not assigned, not Selected, zero merged PRs, no live branches) must still resolve to `entry_blocked`. The new merge check must be additive: it only diverts when a merge signal is genuinely present (ref: Q10).
- **Constraint (logic stays in resolver)** — All new decision logic lives in `qrspi_resolve_state.py`; the batch keeps calling `resolve(state)` verbatim. Any new action requires a matched `RESOLVE_ACTIONS` update in `qrspi-batch.js` (ref: Q4, Q8).

## Delta

- **Modified `scripts/qrspi_pr_state.py`** — `build_state` must surface a merge signal the resolver can trust even when a phase branch was pruned. Two sub-options (see Decision 2): either re-query pruned phase heads for merge state (reusing the `stack_merge_state` machinery already present), or aggregate per-phase `merged` into a stack-level `started`/`merged` verdict the resolver reads. The per-phase `merged` field already exists; the gap is that a pruned branch returns the empty `parse_pr_nodes([])` shape with `merged=False` (ref: Q2, Q11).
- **Modified `scripts/qrspi_resolve_state.py`** — Add a "design already landed" predicate consulted before/inside the entry gate, so design-branch absence + a merge signal routes into the active-phase/implementation logic rather than `entry_blocked`/`run_design`. The partially-landed stack reuses the existing `land` action (Decision 1 Option A, confirmed by RQ1 — no new action). No extra merge guard is added to the `run_design` branch (RQ3 — that re-creation path is unreachable because a merged-design ticket has already left `Selected`) (ref: Q5, Q6, Q9).
- **Modified `.claude/workflows/qrspi-batch.js`** — Only if a new action is introduced: add it to `RESOLVE_ACTIONS` and the dispatch switch, mapping it to the landing worker (ref: Q4, Q8).
- **Modified `scripts/qrspi_resolve_state_test.py`** — Extend `_phase`/`_slice`/`state` (or `_impl`) with a `merged`/merge-signal dimension and add the merged-lower / open-upper case asserting the landing action, plus a regression case proving a genuinely un-started ticket still yields `entry_blocked` (ref: Q12, Q13).
- **Possibly modified `scripts/qrspi_pr_state_test.py`** — If `build_state`'s merge re-query path changes, cover the pruned-head-returns-merged case at the gather layer.

## Pattern Decisions

### Decision 1: How to express "finish landing the remaining slices"

| Option | Approach | Pros | Cons |
|--------|----------|------|------|
| A | Reuse the existing `land` action. Make the entry gate fall through to the implementation/land branch when design is merged-and-gone; `land`'s completeness gate already checks slices are approved + clean. | No new action; no `RESOLVE_ACTIONS`/`qrspi-batch.js` change; smallest blast radius; `land`'s worker (`doLand`) already lands the stack bottom-up. | `land` presumes ALL slice branches are live and ALL PRs open+approved (ref: Q5); a partially-landed stack has fewer live slices — `doLand` must tolerate already-merged lower slices. Reason string "land the whole stack" becomes mildly inaccurate. |
| B | Introduce a new action (e.g. `land_remaining`) distinct from `land`, dispatched to the same or an adapted landing worker. | Explicit, self-documenting; reason string can describe the partial state; keeps full-stack `land` semantics pristine. | Requires matched JS update (`RESOLVE_ACTIONS` + switch + worker mapping) per the sync contract (ref: Q4, Q8); larger surface; two near-identical landing paths to maintain. |

**Recommendation:** Option A
**Rationale:** The codebase already treats `land` as "the stack's remaining open+approved PRs are ready to merge bottom-up" and `doLand` lands bottom-up (ref: Q5, Q8). The discovered pattern is to keep the action vocabulary minimal and mirrored in JS (ref: Discovered Patterns); adding `land_remaining` doubles the landing surface for a difference (some lower PRs already merged) that the land worker can absorb. The real fix is getting `resolve` to REACH the land branch, not inventing a new terminal. Verify `doLand`/`gt` tolerates a stack where lower PRs are already merged; if it does not, that intolerance is the multi-slice tip-exclusion bug tracked separately and out of scope here.
**NEW PATTERN?** No — reuses the existing `land` action and the established entry-gate/active-phase structure.

### Decision 2: How the resolver learns the design phase already merged

| Option | Approach | Pros | Cons |
|--------|----------|------|------|
| A | Make `build_state` re-query a pruned/absent phase head for merge state (reuse `stack_merge_state`/`select_pr(prefer="merged")`, already wired into `qrspi_cleanup.py`) and set `phases.design.merged=True` even when `branchExists=False`. The resolver's entry gate then checks `merged` before declaring "nothing begins." | Closes the cross-module asymmetry (ref: Inconsistencies) — `build_state` would treat a deleted-merged head like the reaper does; uses existing, tested merge machinery; truest signal (a real MERGED PR). | Adds a GraphQL re-query for absent heads in the gather (I/O layer, not unit-tested); slightly more `gh` calls per ticket. |
| B | Aggregate a stack-level `started` flag in `build_state`: a ticket is "started" if ANY phase/slice carries `merged=True` OR any branch is live. Resolver entry gate consults `state["started"]` instead of design-branch-only. | Single boolean; resolver change is minimal and obvious; cheap. | Still depends on `merged` being correctly populated, which fails for a pruned head returning the empty `parse_pr_nodes([])` shape (ref: Q2, Q11) — so this likely REQUIRES Option A's re-query underneath to be reliable. |
| C | In the resolver, treat live implementation slice branches as proof the ticket started: if `phases.implementation.branchExists` (any live slice), bypass the design-absence entry gate. | Pure-resolver change, no gather/I-O edit, no extra GraphQL; directly targets the stranding symptom (live upper slices). | Does not satisfy AC2's "design PR has already merged" wording via a merge signal — it infers started-ness from slices, not from merge state; fails the (rare) window where ALL branches including slices were pruned mid-merge (ref: Q11). |

**Recommendation:** Option A as the durable, strictly-required signal (confirmed by RQ2 — the fully-pruned mid-merge window is in scope, so the merge re-query cannot be skipped), optionally surfaced as Option B's `started`/`merged` verdict for a clean resolver read; treat Option C as a complementary fast-path, NOT the sole fix.
**Rationale:** Research identifies the load-bearing root cause as `build_state` losing merge information that the cleanup reaper preserves — a documented cross-module asymmetry where two consumers of the same GraphQL shape treat a deleted-merged head ref contradictorily (ref: Inconsistencies, Q11). Option A reuses the already-built, already-tested `stack_merge_state`/`select_pr(prefer="merged")` machinery (ref: Q2, Q11), aligning `build_state` with the reaper and satisfying AC2's merge-signal wording directly. Option C alone is tempting (smallest change) but keys off slice presence rather than merge state, so it would not survive a fully-pruned mid-merge stack and does not literally satisfy AC2. The pure-logic/I-O split is a consistent codebase pattern (ref: Discovered Patterns), so the re-query belongs in the labeled I/O section of `qrspi_pr_state.py` and the verdict it produces is what the pure `resolve` reads.
**NEW PATTERN?** No for Option A — it extends `build_state` to use merge machinery the reaper already uses. The only genuinely new element is `build_state` re-querying an absent head, which mirrors `qrspi_cleanup.py`'s existing behavior; flag this as a deliberate convergence of the two modules, not a novel pattern.

## Resolved Questions

These were open during drafting and have been answered by review; the resolutions are now binding on the Delta and Pattern Decisions above.

- **RQ1 (was OQ1) — route a partially-landed stack to `land`.** For a partially-landed stack the resolver routes to the existing `land` action (Decision 1 **Option A**), even though `doLand` may currently choke on already-merged lower slices. The land-worker tolerance fix is the out-of-scope multi-slice tip-exclusion bug tracked separately (see Risk Register row 2); we do NOT introduce a new "needs manual finish" actionable state. This keeps the action vocabulary minimal and mirrored in JS (no `RESOLVE_ACTIONS`/`qrspi-batch.js` change), consistent with Decision 1's recommendation; the resolver's job here is purely to REACH the `land` branch.
- **RQ2 (was OQ2) — the merge re-query is required.** The rare fully-pruned mid-merge window (design, plan, AND all merged slice branches pruned, only the highest open slice's branch live) IS in scope. Therefore the slice-presence fast-path (Decision 2 Option C) is NOT sufficient on its own: `build_state` must re-query the absent/pruned design head for merge state (Decision 2 **Option A**) so the "design already landed" signal survives even when every lower branch is gone. Option C remains a complementary fast-path but the merge re-query is the load-bearing, strictly-required signal.
- **RQ3 (was OQ3) — the re-creation path is unreachable; no extra guard needed.** Guarding `run_design` against re-creating an already-landed design phase for a design-pruned-but-still-`assigned+Selected` ticket is unnecessary: that path is unreachable in practice because a ticket whose design (and lower phases) have merged has already left `Selected` (its reporting status advanced to `Design Review`/`Plan Review`/`Code Review`). No additional merge guard is added to `run_design`; the entry-gate merge check (AC2) already diverts the in-flight case before `run_design` is reached.
