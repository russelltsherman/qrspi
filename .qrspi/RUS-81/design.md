# Design — CI-gated revision: resolver reacts to CI check state and auto-revises red frontier PRs

**Ticket:** RUS-81

## Current State

The PR-state gather issues one GraphQL query (the module-level `PR_QUERY` in `qrspi_pr_state.py`) selecting `number, state, merged, mergedAt, reviewDecision, reviewThreads, comments` per PR node; there is NO `statusCheckRollup` or any check/CI selection anywhere in the repo (ref: Q1, Q10). The gather therefore cannot distinguish "no checks" from "null rollup" — both are simply absent (ref: Q10). `parse_pr_nodes` reduces those nodes into the normalized per-PR shape `{prExists, number, reviewDecision, unresolvedThreads, merged, state, mergedAt, commentTargets}`, and `build_state` adds `branchExists` per phase and `n` per slice (ref: Q2).

The resolver (`qrspi_resolve_state.py`) is pure and consumes that shape via `phases.<name>` and `phases.implementation.slices[]` (ref: Q2). Its decision branches run in strict source order: (1) entry gate, (2) reset for the lowest NON-frontier `CHANGES_REQUESTED`, (2b) unified feedback handler for the lowest frontier phase carrying a frontier CR and/or unaddressed comments → `revise`, then (3) active-phase logic (submit/wait/advance/land). Both step 2 and 2b sit AHEAD of every wait/advance/land sink; the "awaiting review" `wait` is the last resort (ref: Q4, Q11). Frontier-ness is not a stored field — it is re-derived each call from `existing` (phases whose `branchExists` is true) and the fixed `PHASES` order; a phase is frontier when nothing downstream exists (ref: Q5). CI is ignored entirely today, so a PENDING-CI PR takes the ordinary "awaiting review" path to `wait`, and an approved PR advances without ever consulting checks (ref: Q12).

The legal action vocabulary is the `ACTIONS` tuple (`entry_blocked, run_design, submit, wait, revise, advance, land, reset`), mirrored as `RESOLVE_ACTIONS` in `qrspi-batch.js` for envelope validation only (ref: Q6, Q14). Every decision dict has the fixed key set `{action, phase, nextPhase, resetToPhase, discardPhases, commentTargets, changeRequested, reason}`; `revise` carries `phase`, `commentTargets`, and `changeRequested` (ref: Q6). There is NO JS mirror of the resolver decision logic — the batch only dispatches on `decision.action` in a switch; the single source of truth is the Python `resolve` (ref: Q14). The only resolver value kept in lockstep across JS↔Python is the action vocabulary (`ACTIONS` ↔ `RESOLVE_ACTIONS`) (ref: Q14).

`qrspi_resolve.py` assembles the envelope by calling `build_state` then `resolve` as opaque pure functions, so a new CI field inside `state`/`decision` flows automatically UNLESS the JS consumer must read it at envelope top level — in which case it needs a re-emit helper (like `comment_targets_of`) and a new `build_envelope` parameter/key (ref: Q3). The envelope is byte-pinned: the producer test asserts `json.dumps(env, indent=2)+"\n"` equals the committed `wellformed.json`, so any envelope-shape change is a synchronized 3-file edit (ref: Q3, Q13).

The `revise` worker (`doRevise` in `qrspi-batch.js`) addresses a frontier feedback PR in one pass: a per-comment intent engine replies via `qrspi_comment_reply.py`, and only when a formal CR is present it reads the CR summary + threads via READ-only `gh pr view`/`gh api graphql`, edits artifacts, amends in place via `qrspi_revise_amend.py`, then re-requests review via `gt submit --rerequest-review` (ref: Q7). The worker reads NO CI run/check output today — it has no `gh run view`/checks invocation, and zero check diagnostic detail is available because the gather fetches none (ref: Q15). The harness keeps NO durable per-PR counter or marker; cross-run idempotency is purely STRUCTURAL — loop termination relies on the observable `reviewDecision` flip to `REVIEW_REQUIRED` and on bot replies appearing in threads (ref: Q8). Implementation is one logical phase backed by a slice-PR list, collapsed via "any slice" aggregation: `phase_changes_requested("implementation")` is `any(...)` over slices, comments concatenate across slices, and land/wait gates use `any(...)`/`all(...)` (ref: Q9).

## Desired End State

- **AC1** — A frontier phase PR whose check rollup normalizes to FAILURE/ERROR resolves to `revise` even with no CR and no unaddressed comments. A new resolver branch, slotted immediately after the existing unified feedback handler (2b) and ahead of the active-phase sinks, fires on a red frontier and returns `revise` carrying a `ciFailing=true` flag (ref: Q4, Q11).
- **AC2** — A frontier PR whose rollup is PENDING resolves to `wait`. The new branch routes PENDING explicitly to `wait` so the harness never revises against in-flight CI (ref: Q12).
- **AC3** — SUCCESS or no-checks/null behaves exactly as today. The normalizer maps SUCCESS→green and null/absent→none; the resolver's new branch is a no-op for green/none, so the existing review-state path is unchanged (ref: Q10, Q12).
- **AC4** — The rule applies to all frontier phases (design, plan, implementation). A non-frontier CR still resets at step 2 (CI is a frontier-only signal). For implementation, a CI failure on ANY slice PR triggers `revise` on the implementation phase via the existing "any slice" aggregation (ref: Q4, Q5, Q9). **Incomplete-implementation interaction (resolves review finding #2):** the CI branch is slotted before the entire active-phase block, which for implementation begins with the completeness gate (`qrspi_resolve_state.py:270`) that returns `advance` to build the remaining slices. A slice that is committed but not yet PR'd has no `statusCheckRollup`, so its `ciState` MUST normalize to `none` (the `null/absent→none` mapping); the "any slice red" aggregation therefore only ever sees rollups for slices that actually have an open PR. **Decision: a red *open* slice PR is fixed before building the rest** — i.e. when implementation is incomplete (e.g. 2 of 5 slices built) AND an already-PR'd slice is red, the CI `revise` branch (slotted ahead of the completeness gate) fires first and repairs the red slice before any further `advance` builds slice 3. This keeps the stack from accreting more slices on top of a provably-red lower slice, consistent with the bottom-up build/land invariant. (The unbuilt slices contribute `none`, so they neither trigger nor suppress the branch.)
- **AC5** — The `revise` worker, when `ciFailing` is set, diagnoses the failing checks (reads failing run/check output), fixes code, amends the phase commit, and re-pushes via the existing finalize path; combined reviewer-feedback + CI failure is handled in one pass (ref: Q7, Q15).
- **AC6** — No infinite loop: after N consecutive CI-failure revises on the same PR with no green, the resolver falls to `wait` and surfaces the PR for human attention (cap-then-wait). The cap N is **configurable, default 3** (resolved from `.qrspi/config.json` via `scripts/qrspi_config.py`, OQ1 RESOLVED). The counter carrier mechanism is a Design choice (see Decision 2) (ref: Q8).
- **AC7** — New resolver logic is pure and unit-tested in `scripts/*_test.py` per the existing table-driven convention; the action vocabulary stays in lockstep across `ACTIONS`/`RESOLVE_ACTIONS` and the byte-pinned contract fixtures are updated in sync (ref: Q13, Q14).

## Pattern Decisions

### Decision 1: Reuse `revise` action vs. new `ci_revise` action

| Option | Approach | Pros | Cons |
|--------|----------|------|------|
| A | Reuse `revise` with an additive `ciFailing` flag on the decision | No `ACTIONS`/`RESOLVE_ACTIONS` lockstep change; worker dispatch unchanged; CI is "an additional trigger for the existing revise action" per the ticket constraint; combined feedback+CI handled in one `doRevise` pass | `doRevise` must branch internally on `ciFailing` |
| B | New `ci_revise` action string | Cleaner dispatch separation | Adds an action to BOTH `ACTIONS` and `RESOLVE_ACTIONS` (lockstep edit, Q14); a new `doX` handler; cannot cleanly co-handle a PR with both CR and CI failure in one pass |

**Recommendation:** Option A
**Rationale:** The ticket explicitly states CI gating is "an additional trigger for the existing `revise` action, not a replacement," and AC5 requires combined feedback+CI in one pass. The additive-field discipline (research Discovered Patterns) makes `ciFailing` a natural sibling of `changeRequested`, extending the `decision()` helper's fixed key set exactly as prior additive fields did (ref: Q6).
**NEW PATTERN?** No — mirrors the existing `changeRequested` flag on `revise`.

### Decision 2: Durable attempt-counter carrier for the loop cap (AC6)

| Option | Approach | Pros | Cons |
|--------|----------|------|------|
| A | Count consecutive bot-amend commits since the last non-bot/non-amend change via `git log` on the PR head (observable from the repo) | Stateless/structural — honors the no-stored-state invariant (Q8); resolver stays pure (count gathered, fed in) | Requires a reliable "CI-failure amend" marker in the commit trailer to count only CI revises, not feedback revises; still needs an explicit reset point because the worker never runs on green |
| B | Marker comment on the PR (bot posts/increments a hidden counter comment) | Explicit, easy to read via existing `gh` reads | A new write surface; pollutes the PR thread; another idempotency concern |
| C | Amend trailer on the phase commit (e.g. `CI-Revise-Attempt: N`), parsed by the gather into the additive `ciReviseAttempt` field and fed to the resolver | Durable, travels with the amended commit `qrspi_revise_amend.py` already preserves verbatim (Q7); observable; no extra write surface | Trailer parsing (`ci_revise_attempt`) and the carrier field (`ciReviseAttempt`) added to the gather Delta; must increment carefully so a feedback-only amend does not inflate it |

**Recommendation:** Option C
**Rationale:** `qrspi_revise_amend.py` already preserves the commit message + trailers verbatim on every amend (ref: Q7), so a `CI-Revise-Attempt` trailer is a natural, observable carrier that respects the statelessness invariant (the count is re-read from GitHub each run, never stored locally) (ref: Q8). The gather parses it via `ci_revise_attempt` and exposes it as the additive `ciReviseAttempt` field on the per-PR shape; the pure resolver reads that field, compares against N, and falls to `wait` at the cap, matching the precedence-ordered, structural-idempotency patterns. Option A is close but relies on a marker anyway to distinguish CI revises from feedback revises, so C is the cleaner explicit form. **Reset is NOT automatic** (correcting an earlier draft claim, per review finding #1): because the verbatim-preserving amend never zeroes the trailer and the worker never executes on green (green routes to `advance`/`wait`, not `revise`), the design pairs the trailer with two explicit reset mechanisms — (a) the gather forces the *resolver-read* effective count to `0` whenever the current `ciState` is not `red`, and (b) the `doRevise` writer overwrites the trailer to `0` on every non-CI amend. Together these make the counter measure *consecutive* red-CI revises with no green in between (AC6), not a lifetime total — the exact failure the ticket's "counter must not falsely inflate" risk called out.
**NEW PATTERN?** Yes — there is no per-PR durable counter today (ref: Q8). Justified because the cap (AC6) is inherently cross-run state with no existing carrier; the trailer keeps it observable-from-GitHub rather than breaking the stateless-reconciliation invariant.

### Decision 3: Resolver precedence slot for the CI branch

| Option | Approach | Pros | Cons |
|--------|----------|------|------|
| A | New branch immediately after the unified feedback handler (2b), before the active-phase block | Reset (non-frontier CR) still wins; frontier feedback (CR/comments) still wins; CI fires only on a frontier with no outstanding feedback — exactly the ticket's "ahead of the wait sink, after reset" requirement | None material |
| B | Fold CI into the existing 2b feedback set | Single branch | Conflates CI signal with comment/CR semantics; harder to attach `ciFailing` distinctly; risks masking feedback ordering |

**Recommendation:** Option A
**Rationale:** The ticket's Known risks demand the CI branch slot "after the reset check, adjacent to the frontier feedback handler, ahead of the wait sink." A discrete branch after 2b preserves the documented invariant that `revise` (feedback) precedes `wait`, and that a non-frontier CR resets before any frontier handling (ref: Q4, Q11). Precedence is the sole conflict-resolution mechanism (no scoring), so an explicit ordered slot is the idiomatic fit (ref: Q11).
**NEW PATTERN?** No — adds one branch to the existing precedence-ordered chain.
