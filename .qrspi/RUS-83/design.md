# Design — CI-revise loop cap must count failed revise attempts (close AC6 hole from RUS-81)

**Ticket:** RUS-83
**Research basis:** research.md @ 2026-06-15T00:00:00Z
**Generated:** 2026-06-15T00:00:00Z
**Status:** draft

## Current State

The `CI-Revise-Attempt: N` counter has a single durable store: the head-commit trailer. There is no on-disk state; the gather re-derives the effective count from the GraphQL head-commit message every run (ref: Q1, Q5). The trailer is written **only** by an LLM-worker `gt modify --no-interactive -m "..."` spawned inside `doRevise` — there is no deterministic Python/JS code that writes it (ref: Q1).

Reading the counter is a two-stage pipeline. The gather's `ci_revise_attempt(message)` parses the trailer to an int (last-occurrence wins), and `parse_pr_state` emits `ciReviseAttempt`, but forces it to `0` whenever `ciState != "red"` (ref: Q4, Q6). The resolver's `ci_revise_attempt_of` reads that field directly (taking `max(...)` across implementation slices) and compares `attempt < ci_revise_cap` in its CI precedence slot, returning `revise` under cap and `wait` at/above cap (ref: Q5, Q7).

The trailer increment is bundled into the worker's content-fix flow: the worker is told to SKIP the content amend when nothing changed and to write the `<prior + 1>` trailer only "for EACH branch you touched in this pass" (ref: Q8, Q9). When the worker reports failure with no commit pushed, `finResult` records a failure result but mutates no commit, so the next batch run re-reads the identical trailer and the resolver re-emits the same `revise` (ref: Q2, Q8). This is the non-progressing loop the ticket targets: counter advancement is coupled to a *successful content amend*, so a perpetually-failing worker loops forever below the cap (ref: Q2, Q8, Q9, Inconsistencies). There is **no** orchestrator-side write point that advances the counter on worker failure (ref: Q11).

The resolver's `wait` decision is a flat dict with `action`, `phase`, `ciFailing` (bool), and a free-text `reason`; there is no structured field that distinguishes "gave up after failed attempts" from a normal cap-reached park — the only differentiator is prose (ref: Q10, Q14). The two existing resets are: read-side not-red→0 in the gather (the load-bearing correctness gate) and writer-side `resetCiReviseTrailer` in `doRevise` (hygiene only) (ref: Q6). All commit mutation is delegated to spawned workers running `gt`, never raw git in JS; `resetCiReviseTrailer` is the existing precedent for a deterministic, content-free, worker-spawned `gt modify -m` that sets a trailer value (ref: Q11, Discovered Patterns). The resolver and gather are pure and unit-tested via stdlib-only `_test.py` siblings run by `run_tests.py`; resolver cap cases feed `ciReviseAttempt` directly as a synthetic field rather than exercising the trailer parser (ref: Q12, Q13).

## Desired End State

- **AC1 — every attempt counts, including failed-no-change.** A red-frontier revise pass that ends with the worker reporting failure and pushing no content amend must still advance `CI-Revise-Attempt` by one. This is achieved by making a **deterministic Python helper (`scripts/qrspi_ci_revise_bump.py`) the SOLE increment authority** (Decision 1 Option A′): after the revise worker returns on a red pass, `doRevise` runs the helper once per still-red branch, **unconditionally** — it reads the prior count off the branch head commit, writes `CI-Revise-Attempt: <prior+1>`, and publishes. The worker no longer writes the trailer on the CI path, so there is exactly one writer and no need to detect "did the worker advance it." Because the helper is deterministic (Python + `gt` subprocess, verify, non-zero exit on failure — the `qrspi_revise_amend.py` model), the advance is a real guarantee rather than best-effort (ref: Q1, Q2, Q8, Q11).
- **AC2 — bounded termination.** After the configured number of consecutive red-CI revise attempts (fixed-but-still-red or failed-no-change), the resolver parks the PR as `wait` and stops re-revising. The existing `attempt < ci_revise_cap` comparison already enforces this once AC1 guarantees the count advances every pass (ref: Q7).
- **AC3 — green still resets.** A revise that turns CI green resets the counter to 0 via the existing read-side not-red→0 gather reset, so the cap measures *consecutive* unresolved red episodes (ref: Q6). RUS-81 reset behavior is unchanged.
- **AC4 — distinguishable terminal state.** The cap-reached `wait` carries a structured signal letting the operator see the PR "needs manual diagnosis after repeated failed attempts," not just a normal park. A new boolean field on the decision (e.g. `ciGaveUp`) plus a distinct reason expresses this (ref: Q10, Q14).
- **AC5 — pure, unit-tested termination logic.** The cap comparison and the new terminal-state field live in the pure resolver and are covered by new `qrspi_resolve_state_test.py` cases; the deterministic increment helper (if a new script) gets its own `_test.py` (ref: Q12, Q13).

## Delta

- **New deterministic increment helper `scripts/qrspi_ci_revise_bump.py` — the SOLE increment authority (the core fix, Decision 1 Option A′).** A self-locating Python script (mirroring `qrspi_revise_amend.py`) invoked as `python3 scripts/qrspi_ci_revise_bump.py --ticket <id> --branch <branch>`. It: (1) checks out `<branch>` (`gt checkout --no-interactive`); (2) reads the head-commit full message (`git log -1 --format=%B`); (3) parses the existing `CI-Revise-Attempt: N` (absent ⇒ `prior=0`) and rewrites the message with **exactly one** `CI-Revise-Attempt: <prior+1>` trailer, preserving the subject and every other trailer byte-for-byte; (4) applies it message-only (`gt modify --no-interactive -m`); (5) re-publishes (`gt submit --publish --no-edit [--stack for implementation] --no-interactive`) so the bump reaches GitHub even when the content worker pushed nothing; (6) VERIFIES exactly one trailer at `<prior+1>` and prints JSON `{ ok, branch, prior, new, error? }`, exiting non-zero (fail-closed) on any failure. The **trailer parse+rewrite is a pure function** with a `_test.py` (AC5); the `gt` calls are the imperative shell, exactly as `qrspi_revise_amend.py` splits them.
- **Modified `.claude/workflows/qrspi-batch.js` (`doRevise`):** (a) in the CI-failure branch, **DELETE the worker-prompt step-6 `CI-Revise-Attempt` trailer write** (the worker now only diagnoses, fixes, amends content, and re-requests review — it never touches the counter); (b) after the worker returns on a red pass, run the helper **unconditionally** for each still-red branch — for design/plan the one phase branch; for implementation, once per still-red slice branch (lowest first), preserving the resolver's `max(...)` consecutive-red semantics — via a thin worker that types the one verbatim `python3 … qrspi_ci_revise_bump.py …` command (the `qrspi_revise_amend.py` invocation model: determinism lives in Python, the worker exercises no judgment). The increment runs whether the worker returned `ok:true` or `ok:false`, since the worker is no longer a counter writer. The non-CI comment-only reset-to-0 path (`resetCiReviseTrailer`) is **unchanged**.
- **Modified `scripts/qrspi_resolve_state.py`:** add a `ciGaveUp` field to the `decision` builder (default `False`); set it `True` on the cap-reached red→`wait` branch and emit a distinct reason. No change to the `attempt < cap` comparison itself.
- **Modified `scripts/qrspi_pr_state.py`:** no functional change — the helper writes the identical `CI-Revise-Attempt: N` trailer the gather already parses; confirm only that the parser tolerates the helper-written value identically to the (former) worker-written one (it does: same trailer, same regex).
- **New/modified tests:** new `scripts/qrspi_ci_revise_bump_test.py` for the pure trailer parse/rewrite core (absent⇒1, N⇒N+1, exactly-one-trailer, subject/other-trailers preserved); resolver cases for the cap-reached `ciGaveUp` field in `qrspi_resolve_state_test.py`. The JS wiring (unconditional helper invocation, step-6 deletion) is covered by a manual end-to-end run on a deliberately-unfixable red PR (per CLAUDE.md the JS shell is not unit-tested). All Python runs under `run_tests.py`.

## Pattern Decisions

### Decision 1: Where — and how — the failed-attempt increment is performed

The increment authority is the crux of this ticket. The first framing (A vs B) compared *adding* an orchestrator write on top of the worker's existing one; review surfaced that this leaves **two** increment authorities (worker step-6 + orchestrator) that must be reconciled to avoid double-counting, and that the "orchestrator increment" as a spawned LLM worker is *not* deterministic — Risk Register row 1 admits a `gt` flake leaves the count stuck below cap, which is the **same** non-advancing-counter failure this ticket exists to close. Option **A′** below resolves both problems and is the recommendation.

| Option | Approach | Pros | Cons |
|--------|----------|------|------|
| **A′ (recommended)** | **A deterministic Python helper `scripts/qrspi_ci_revise_bump.py` is the SOLE increment authority.** It reads the branch head message, sets exactly one `CI-Revise-Attempt: <prior+1>` trailer (prior parsed off the commit — absent⇒0), `gt modify -m`, then `gt submit --publish`, VERIFIES, and exits non-zero on failure. `doRevise` runs it (once per still-red branch) after the worker returns on a red pass, UNCONDITIONALLY. The worker's own step-6 trailer write is **removed** on the CI path. | **Single writer** ⇒ no double-counting, no need to detect "did the worker advance it" (no post-pass re-read). **Genuinely deterministic** (Python + `gt` subprocess, like `qrspi_revise_amend.py`) ⇒ AC1 is a real guarantee, not best-effort; a failure exits non-zero and is *surfaced*, not silently stuck. The trailer-rewrite is a **pure, unit-tested** function (AC5). `prior` is read off the commit, so no need to thread it through the envelope. Publishes on the failed path, so the next gather sees the bump. | One new script + its `_test.py`; the worker prompt loses its step-6 (a deletion, low risk); the helper run is still invoked via a thin worker that types one verbatim command (the `qrspi_revise_amend.py` trust model — no LLM judgment in the write). |
| A | Orchestrator-side increment in `doRevise` (worker-spawned content-free `gt modify -m`, mirroring `resetCiReviseTrailer`) **in addition to** the worker's existing step-6 write | Reuses the content-free trailer-write pattern; fires on the failure path | **Two write authorities** ⇒ must re-read the post-pass trailer and compare to `prior` to avoid double-counting (added complexity); still an LLM worker ⇒ **best-effort, not deterministic** (Risk row 1: a `gt` flake leaves the count stuck — partial AC1) |
| B | Have the worker itself always write `<prior+1>` even on failure | Single write site | Violates the worker honesty contract / no-fabrication intent; a failing worker is exactly the case we cannot trust to run a step (ref: Q2, Q8) |
| C | Move the counter to on-disk state incremented deterministically by the orchestrator | Fully deterministic, no trailer coupling | Violates the "trailer-as-only-durable-state" and "resolver-pure, count gathered" constraints (ref: Q5, ticket constraints) |

**Recommendation:** Option A′ — a deterministic Python helper as the **sole** increment authority.
**Rationale:** The ticket's AC1 is a *determinism* requirement ("every attempt counts, including failed-no-change"). Option A delivers that only best-effort because the writer is an LLM worker (Risk row 1) — closing a non-advancing-counter bug with a mechanism that can itself fail to advance is circular. A′ moves the write into deterministic Python (the `qrspi_revise_amend.py` precedent: a Python script that runs `gt` via subprocess, verifies, and fails closed) and makes it the *only* writer by deleting the worker's step-6 CI-path increment. Single-writer kills the double-count problem and removes the post-pass trailer re-read the A framing needed (review finding: the worker return shape `{ok, prUrl, newStatus, summary}`, ref Q3, has no "trailer advanced" field, so A had to infer advancement by re-reading the commit — A′ needs no such inference because nothing else writes). `prior` is read off the commit by the helper, so it need not be threaded through the decision (which carries no numeric attempt field — only `ciFailing` + prose `reason`, ref Q10). It preserves trailer-as-durable-state and resolver-purity. B is barred by the honesty contract; C breaks no-disk-state.
**NEW PATTERN?** No — it is the `qrspi_revise_amend.py` pattern (a deterministic, self-locating Python `gt` helper with a pure tested core) applied to the trailer write, and it *subsumes* the `resetCiReviseTrailer` mechanism's role on the CI path. (The non-CI reset-to-0 path is untouched and out of scope; the helper could later generalize to a `--set <N|bump>` form to unify both, but that is not required here.)

### Decision 2: How the terminal "gave up" state (AC4) is represented

| Option | Approach | Pros | Cons |
|--------|----------|------|------|
| A | New boolean field `ciGaveUp` on the `decision` dict, set on the cap-reached red→`wait` branch | Structured, machine-readable; additive; backward-compatible; trivially unit-testable in the pure resolver (ref: Q10, Q13) | One more field on every decision (defaulted `False`) |
| B | Encode it only in the free-text `reason` string | Zero schema change | Not machine-readable; AC4 asks the operator be able to *see* the distinction reliably — prose is the current inadequate state (ref: Q10, Q14) |
| C | A new distinct `action` value (e.g. `gave_up`) | Maximally explicit | Expands the `ACTIONS` enum and the JS dispatch switch; over-engineered when `wait` semantics are correct — the PR is parked either way (ref: Q10) |

**Recommendation:** Option A
**Rationale:** The decision dict is already the structured contract the JS dispatch and result-recording consume; adding a defaulted boolean is additive and backward-compatible per the ticket constraints (ref: Q10, Q14). It mirrors the existing `ciFailing` boolean precedent. Option B leaves AC4 in prose (the inadequate status quo); Option C needlessly grows the action enum when the action genuinely is `wait`.
**NEW PATTERN?** No — mirrors the existing `ciFailing` boolean field on the decision.

### Decision 3: Distinguishing failed-no-change from content-changing-but-red attempts at the cap

| Option | Approach | Pros | Cons |
|--------|----------|------|------|
| A | Track only the trailer count; set `ciGaveUp=True` whenever the cap is reached on red CI (no per-attempt success/fail breakdown) | Simplest; the operator action is identical (manual diagnosis) regardless of which attempts failed; the trailer already cannot encode per-attempt outcome (ref: Q9) | Loses the failed-vs-ineffective nuance — but AC4 only asks to flag "needs manual diagnosis" |
| B | Add a second trailer (e.g. `CI-Revise-Failed: M`) counting only no-change failures | Full breakdown | A second trailer to write/read/reset on two code paths; the gather/resolver contract grows; AC4 does not require this granularity |

**Recommendation:** Option A
**Rationale:** AC4 asks the operator to see "the PR needs manual diagnosis after repeated failed attempts" — a single cap-reached `ciGaveUp` flag satisfies that. The trailer carries only a count and cannot encode per-attempt outcome (ref: Q9), and the human action is identical either way. Option B doubles the durable-state surface for nuance the ticket does not require (and Out-of-Scope keeps cap mechanics minimal).
**NEW PATTERN?** No.

## Open Questions

- OQ1: When the increment helper exits non-zero (a real `gt`/publish fault), should `doRevise` record the revise pass as a **hard failure** the operator must see (recommended, since the helper is deterministic and a non-zero exit is a genuine error, not LLM flakiness), or absorb it best-effort like `resetCiReviseTrailer`? Recommended: surface it as a recorded failure on the result record so a count that could not advance is never silent. (Affects the strength of the AC1/AC2 termination guarantee.)
- OQ2: Should `ciGaveUp` (AC4) be raised on *every* cap-reached red→`wait`, or only when the cap was reached with at least one failed-no-change attempt? (Decision 3 recommends the former for simplicity; confirm the operator-facing semantics intended by AC4.)
- OQ3: For implementation phases with multiple slices, the resolver aggregates attempts via `max(...)` (ref: Q5). The design runs the helper on **only the still-red** slice branches each pass (a green/pending slice is not re-bumped). Confirm this yields the intended consecutive-red semantics: each still-red slice advances its own trailer, `max(...)` tracks the longest streak, and a slice that goes green is zeroed by the gather's read-side not-red→0 reset — so the cap reflects the worst still-failing slice. (No structured per-slice attempt breakdown is added; matches Decision 3 Option A.)
